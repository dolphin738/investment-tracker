## 2. I-01 编辑界面统一（体验优化 · P1）

### 2.1 背景与问题

当前 `features/security-trade/security-trade-form.tsx` 存在**录入态 / 编辑态分叉**：

- **录入态**：展示「方向 / 日期 / 标的 / 数量 / 单价 / **费用三框（佣金 / 印花税 / 其他）** / 备注」+ 成交额只读预览；保存时联动创建 `FeeRecord`（`transactionId` 关联）。
- **编辑态**：**不展示费用三框**、不重算 FeeRecord（代码注释 U-4）；后端 `update` 忽略 `fee`。→ 用户编辑一笔买卖时看不到费用，也无法修正费用，界面与录入不一致。

分红/费用表单（`dividend-fee-form.tsx`）已为录入/编辑共享同一组件，字段一致；本次以它为基准对齐买卖流水。

### 2.2 用户故事

- **US-I01-1**：作为用户，我希望**编辑买卖流水时看到与录入完全相同的界面**（字段、布局、校验、预览），这样我不需要重新学习操作，且能修正包括费用在内的全部字段。

### 2.3 验收标准（检查清单）

1. 编辑买卖流水弹窗与录入弹窗**使用同一表单组件**（`SecurityTradeForm` 复用），仅初始值不同（编辑时回填该笔记录全部字段）。
2. 字段集合与顺序完全一致：**方向 → 日期 → 标的 → 数量 → 单价 → 费用（佣金/印花税/其他）→ 备注**。
3. **编辑态也展示费用三框**，回填该笔已关联 FeeRecord 的费用明细（按费用类型拆分回显）；未关联则费用三框为空。
4. **成交额预览一致**：买入 `q×p+fee`、卖出 `q×p−fee`（只读实时预览），编辑时随数量/单价/费用变化同步刷新。
5. 校验规则一致：`quantity > 0`、`price > 0`、`fee ≥ 0`、日期不可未来、卖出数量硬校验（「当前持有 X，最多可卖 X」）。
6. **编辑保存时允许更新费用**：后端 `SecurityTrade` update 契约支持 `fee` 字段（当前忽略 `fee`，需补齐）；联动更新/新建/删除关联 FeeRecord（与录入态对称，U-4 行为反转）。
7. 保存后行为一致：toast 反馈、持仓列表刷新、自当日起自动总资产记录重建（手工记录日期跳过）、`CASH-P0-05` 买卖后现金余额软提示。
8. 分红/费用记录编辑界面保持与录入一致（含 I-02 所得税字段、I-03 场景字段）。

### 2.4 边界情况

- 编辑历史日期流水 → 从该日起级联重算（`recalculation.service`），toast 提示影响范围。
- 编辑时把费用从「有」改为「无」→ 删除关联 FeeRecord；从「无」改为「有」→ 新建；改金额 → 更新。
- 编辑时修改卖出数量超过该日持仓 → 拒绝保存并明确提示。
- 空值统一显示 `-`；金额右对齐 + 等宽字体（沿用 `FLOW-P0-07` 风格）。

## 3. I-02 分红所得税修复（Bug · P0）

### 3.1 问题描述与根因（已定位）

**现象**：编辑分红记录、输入所得税额后保存失败，后端返回「property type should not exist」。

**根因（供架构师直接复现/验证）**：

1. `packages/backend/src/main.ts` 全局 ValidationPipe 开启 `whitelist: true, forbidNonWhitelisted: true` —— 提交 DTO 未声明的属性即被 400 拒绝。
2. `packages/backend/src/modules/dividend/dto/update-dividend-record.dto.ts`（`UpdateDividendRecordDto`）**未声明 `type` 字段**；而创建 DTO（`CreateDividendRecordDto`）声明了 `type?: DividendType`。
3. 前端 `dividend-fee-form.tsx` 在**编辑分红**时提交 payload 携带 `type`（`DividendType`）→ 被 `forbidNonWhitelisted` 拒绝 →「property type should not exist」。
4. 附带缺口：`DividendService.update()` 目前只处理 `securityId / date / amount / tax / note`，**即使 DTO 放行 `type` 也不会落库**，须一并补齐。

### 3.2 用户故事

- **US-I02-1**：作为用户，我希望录入分红时所得税**可填可不填**，之后编辑也能**随时补充或修改**所得税，并且无论哪种情况，页面都正确显示**分红净额**。

### 3.3 验收标准

#### 3.3.1 DTO 校验规则（明确）

| 字段 | Create DTO | Update DTO（修复后） | 校验规则 |
|------|-----------|---------------------|---------|
| `securityId` | 必填 `@IsUUID()` | 可选 `@IsUUID()` | 二级校验：标的必须属于该组合 |
| `date` | 必填 `@IsDateString()` | 可选 `@IsDateString()` | `YYYY-MM-DD`；不可未来（服务层） |
| `amount` | 必填 `@IsDecimal({decimal_digits:'0,2'})` | 可选 `@IsDecimal({decimal_digits:'0,2'})` | **> 0**，字符串传输 |
| `tax` | 可选 `@IsOptional() @IsDecimal({decimal_digits:'0,2'})` | 可选 `@IsOptional() @IsDecimal({decimal_digits:'0,2'})` | **≥ 0**；空 / 未传 = 0 |
| `type` | 可选 `@IsOptional() @IsEnum(DividendType)` | 🔴 **必须补上**：`@IsOptional() @IsEnum(DividendType)` | `CASH` / `STOCK_DIVIDEND`，缺省 `CASH` |
| `note` | 可选 `@IsString() @MaxLength(200)` | 可选 `@IsString() @MaxLength(200)` | — |

> 🔴 修复动作（后端两处）：
> 1. `UpdateDividendRecordDto` 增加 `type?: DividendType`（含装饰器）。
> 2. `DividendService.update()` 增加 `...(dto.type !== undefined && { type: dto.type })` 落库分支。

#### 3.3.2 三场景数据流（必须全部通过）

| 场景 | 用户操作 | 提交 payload（示意） | 后端处理 | 落库结果 | 展示净额 |
|------|---------|---------------------|---------|---------|---------|
| **① 录入时填写所得税** | 新增分红，金额 320.00、所得税 60.00 | `{securityId, date, amount:'320.00', tax:'60.00', type:'CASH'}` | Create DTO 通过 → `parseAmount(320)` / `parseTax(60)` / `validateNetAmount(320−60=260≥0)` | `{amount:320.00, tax:60.00}` | **260.00** |
| **② 录入时未填写所得税** | 新增分红，金额 320.00，所得税留空 | `{securityId, date, amount:'320.00', type:'CASH'}`（tax 不传） | Create DTO `tax` 可选 → `parseTax(undefined) → 0`（schema 默认 0） | `{amount:320.00, tax:0.00}` | **320.00** |
| **③ 后续编辑补充所得税** | 编辑场景②的记录，补充所得税 60.00 | `{amount:'320.00', tax:'60.00', type:'CASH'}` | Update DTO 通过（含 `type`）→ resolve 现值 + 更新值 → `validateNetAmount(320−60=260≥0)` → 更新 `tax` | `{amount:320.00, tax:60.00}` | **260.00** |

#### 3.3.3 净额计算口径（与既有口径一致）

- **净额 = 分红金额 − 所得税**（`netAmount = amount − tax`）。
- **后端统一计算**（`DividendService.toResponse()`），前端**不自行二次计算**（延续 K-2）；展示 2 位小数（`toFixed(2)`）。
- `netAmount` **不落库**，为运行时响应字段（Prisma schema 零新增列，维持 `amount` + `tax` 两列）。
- 存量数据 `tax` 为空 → 防御回退 0（服务已有）。

#### 3.3.4 校验与错误提示

| 校验项 | 规则 | 错误提示 |
|--------|------|---------|
| 所得税格式 | `@IsDecimal({0,2})` | 「所得税格式非法」（服务层兜底） |
| 所得税为负 | `tax ≥ 0` | 「所得税不能为负」 |
| 净额为负 | `amount − tax ≥ 0` | 「净额不能为负」 |
| 分红金额 | `amount > 0` | 「分红金额必须大于 0」 |

#### 3.3.5 前端要求

1. 编辑分红弹窗的所得税输入框**可编辑**并**回填现有 tax**（编辑模式下不再禁用）。
2. 提交 payload 同时携带 `tax` 与 `type`（保证 `type` 不被 `forbidNonWhitelisted` 拦截）。
3. UI 实时预览净额（只读预览，最终以服务端返回为准）。
4. 保存成功 → 列表净额列更新；无「property type should not exist」报错。

### 3.4 边界情况

- `tax = amount` → 净额 0，**允许**（不报错）。
- `tax > amount` → 400「净额不能为负」。
- 编辑时只改 tax 不改 amount → 净额按新 tax 重算。
- 编辑时修改 `type`（如 `CASH` → `STOCK_DIVIDEND`）→ 保存成功（本次一并支持）。
- 红利再投（`STOCK_DIVIDEND`）时 tax 通常为 0，但**允许填写**（仅信息记录，不强制）。
- 回归确认：分红仍**不参与** XIRR / 净值计算（D-02 / C-08′），不触发重算。

## 4. I-03 费用记录合并（功能新增 · P1）

### 4.1 背景与问题

当前 `FeeRecord` 每条费用独立一行（`date / securityId / amount / type / transactionId / note`）：同一时间同一标的的多笔费用分散显示；且**无法区分该费用发生在买入时还是卖出时**（`FeeType` 只有 COMMISSION / STAMP_TAX / OTHER，与场景无关）。

### 4.2 需求定义

#### 4.2.1 合并规则（明确）

- **合并键（Merge Key）** = `(portfolioId, securityId, date, scenario, type)`。
  - `date`：费用发生日期（**同一时间 = 同一日期**；FeeRecord 无时间戳字段，按自然日对齐）。
  - `securityId`：同一标的。
  - `scenario`：费用场景（新增，见 4.2.3）。
  - `type`：费用类型（COMMISSION / STAMP_TAX / OTHER）。
- **合并语义**：同一合并键的多笔费用 → **合并为一条记录，金额 = 各笔合计**（`amount` 相加，2 位小数）。
- **不合并的情况**：日期不同 / 标的不同 / 场景不同 / 类型不同，任一不同即分开记录。
- **展示**：费用列表按合并键聚合展示一行：`日期 / 标的 / 场景（买入时｜卖出时）/ 费用类型 / 合计金额 / 备注 / 操作`；可展开查看组成笔数（可选 P1）。

#### 4.2.2 数据模型影响

| 项 | 说明 |
|----|------|
| `FeeRecord` 新增字段 | `scenario`：枚举 `FeeScenario { BUY, SELL }`（语义：`BUY`=买入时费用，`SELL`=卖出时费用），**非空** |
| 可选唯一约束 | `@@unique([portfolioId, securityId, date, scenario, type])` —— 数据库层强制合并；同一合并键写入走**累加 upsert**（amount 相加）而非报重复 |
| `transactionId` | 保留为可选关联；合并后逐笔关联语义弱化（指向代表流水或最近一笔，见 §7 开放问题 Q-3） |
| Migration | 新增 `scenario` 列 + 可选唯一索引；存量数据场景默认值策略见 §7 开放问题 Q-4 |
| 计算参与度 | **不参与收益计算**（D-03 延续，不触发重算，不进 CashFlow） |

#### 4.2.3 「买入时 / 卖出时」的判定与展示

- **录入判定（主）**：费用记录表单新增「场景」必填选择器（买入时 / 卖出时）。
- **自动推断（辅助）**：若 `transactionId` 指向某笔 `SecurityTrade`，按该流水 `side` 自动推断默认场景（`BUY_SEC → 买入时`、`SELL_SEC → 卖出时`），用户可修改。
- **展示**：列表 / 明细 / 汇总中场景以**徽标**呈现（「买入时」「卖出时」），并可被 I-05 统一筛选器的「场景」维度过滤。
- **联动**：I-01 买卖流水编辑保存时联动创建/更新的 FeeRecord，场景自动取该笔流水方向。

### 4.3 用户故事

- **US-I03-1**：作为用户，我希望同一时间同一标的的多笔费用自动合并展示，且一眼看出每笔费用是**买入时**还是**卖出时**发生的，这样对账单更清晰、不用逐笔数。
- **US-I03-2**：作为用户，我希望按「场景」筛选费用记录（只看出买入时或卖出时的费用）。

### 4.4 验收标准

1. 同一合并键（同日期 + 同标的 + 同场景 + 同类型）录入多笔 → 列表只显示一条，金额 = 合计。
2. 不同费用类型（佣金 vs 印花税）同日期同标的同场景 → 两条（按类型分别合并）。
3. 同日期同标的同类型但场景不同（买入时 + 卖出时）→ 两条（场景不合并）。
4. 每条费用记录明确展示「买入时 / 卖出时」徽标。
5. 新建费用表单含「场景」必填选择器；从买卖流水联动创建时场景自动推断。
6. 修改 / 删除组成笔后合并结果正确重算（累加式）。
7. 费用仍不参与收益计算（回归：`daily_nav` / `daily_xirr` 不变，`REG-06` 不受影响）。
8. 导出（`SET-P0-03`）费用数据新增 `scenario` 列。

### 4.5 边界情况

- 同一天同一标的有买入时 + 卖出时费用 → 场景不同不合并（两条）。
- 存量数据无 `scenario` → migration 策略（Q-4）：能按 `transactionId` 推断的自动推断；无法推断的统一默认 `BUY` 并提示用户修正，或提供一次性数据修复工具（**需用户确认**）。
- 合并金额精度 2 位小数（`NUMERIC(18,2)`）。
- 并发写入同一合并键 → 唯一约束 + 累加 upsert 需在事务内保证不重复（架构评估）。

## 5. I-04 默认日期范围全局化（功能新增 · P1）

### 5.1 背景与问题

- 设置页「默认日期范围」下拉（`pages/settings.tsx` 的 `DATE_RANGE_OPTIONS`）目前只有 **4 项**：近3月 / 近1年 / 今年至今 / 全部。
- 各处「快捷范围」（`features/query/dimension-switcher.tsx` 的 `QUICK_RANGE_OPTIONS`）为 **7 项**：近一周 / 近1月 / 近3月 / 近6月 / 近1年 / 今年 / 全部。
- `UserPreference.defaultDateRange`（PRD §6.9.1，默认 `1y`）未在所有快捷范围位置全局生效。

### 5.2 需求定义

#### 5.2.1 默认日期范围选项集合（明确）

- 设置页「默认日期范围」下拉 = **与 `QUICK_RANGE_OPTIONS` 完全一致的一组 7 项**：

| value | label |
|-------|-------|
| `1w` | 近一周 |
| `1m` | 近 1 月 |
| `3m` | 近 3 月 |
| `6m` | 近 6 月 |
| `1y` | 近 1 年 |
| `ytd` | 今年 |
| `all` | 全部 |

- **单一真相源**：`QUICK_RANGE_OPTIONS`（`features/query/dimension-switcher.tsx`）。设置页**复用该常量**（共享导出），**不得维护第二份选项数组**（消除两处漂移的根因）。

## 6. I-05 持仓页统一筛选器（体验优化 · P0）

### 6.1 背景与问题

持仓页当前三板块各有独立筛选：
- 【B】持仓列表：`HoldingsToolbar`（持仓日期 + 类型多选 + 显示已清仓，`HOLD-B-P0-11`）。
- 【C】买卖明细：独立筛选（标的 / 日期 / 方向，`HOLD-B-P0-07`）。
- 【E】分红/费用：独立 Tab + 自身筛选（`HOLD-B-P0-10`）。

三套筛选不统一、互不联动，用户切板块要重复设置；「持仓日期卡片」仅是一个单点日期输入，承载能力有限。

### 6.2 需求定义

#### 6.2.1 统一筛选器（核心）

- 持仓 / 买卖明细 / 分红费用 **三个板块共享同一个筛选器**，位于页面顶部、三板块之上。
- **承载容器**：重新设计的「**持仓日期卡片**」升级为统一筛选器容器（见 6.2.3）。
- 任一筛选维度变化 → **三板块同时刷新**；筛选状态写入 URL query（刷新 / 分享后保持）。

#### 6.2.2 筛选维度（明确）

| 维度 | 取值 | 作用板块 | 说明 |
|------|------|---------|------|
| **日期范围** | 快捷范围 7 项 + 自定义起止（复用 `DateRangeQuickPicker` 口径） | 买卖明细 / 分红费用 | 区间内过滤 |
| **持仓日期（as-of）** | 单点日期，默认今日，范围 `[首个交易日, 今日]`（沿用 `HOLD-B-P0-11`） | 持仓板块 | 精确回溯某日持仓 |
| **证券** | 标的多选（全不选 = 全部） | 三板块 | 同源过滤 |
| **场景** | 买入 / 卖出 / 全部 | 买卖明细（按方向）、分红费用（按场景，I-03） | 持仓板块不适用（置灰/隐藏） |
| 类型多选（持仓板块专属） | 股票 / 基金 / 债券 / 其他 | 持仓板块 | 沿用 `HOLD-B-P0-11` |
| 「显示已清仓」开关（持仓板块专属） | on/off | 持仓板块 | 沿用，初值 `UserPreference.showLiquidated` |

> 日期范围 与 持仓日期(as-of) 的关系见 §7 开放问题 Q-6（建议：独立单点，保持精确回溯语义）。

#### 6.2.3 持仓日期卡片重新设计（要点）

- 从「单点日期输入」升级为「统一筛选器容器」，卡片内含：
  1. **快捷范围**下拉（7 项，复用 `QUICK_RANGE_OPTIONS`）+ **自定义起止**日期输入；
  2. **持仓日期（as-of）** 单点输入（带下限/上限校验）；
  3. **证券** 多选下拉（含已选计数徽标）；
  4. **场景** 下拉（买入 / 卖出 / 全部）；
  5. **持仓板块专属**：类型多选 + 显示已清仓开关（可折叠收起，避免卡片过重）。
- 视觉与布局沿用页面卡片风格（`rounded-md border p-3` 体系），保持与录入表单/其他筛选控件同高对齐。
- 卡片标题语义：「统一筛选器」或「筛选」，原「持仓日期」label 内化为 as-of 字段 label。

#### 6.2.4 三板块联动规则（明确）

| 筛选维度变化 | 持仓板块 | 买卖明细板块 | 分红费用板块 |
|------------|---------|-------------|-------------|
| 日期范围 | 不变（持仓以 as-of 为准） | 区间过滤 | 区间过滤 |
| 持仓日期(as-of) | 按 as-of 精确推导 | 不变（以日期范围为准） | 不变 |
| 证券 | 过滤 | 过滤 | 过滤 |
| 场景 | 不适用（置灰） | 按方向过滤（买入/卖出） | 按场景标签过滤（I-03） |
| 类型多选 | 过滤 | 不变 | 不变 |
| 显示已清仓 | 显示/隐藏 qty=0 | 不变 | 不变 |

**联动口径**：各板块只在**适用的维度**上响应筛选，不适用的维度不改动（避免跨口径混淆）；UI 在卡片中注明「持仓板块以持仓日期为准，买卖明细/分红费用以日期范围为准」。

#### 6.2.5 URL query 持久化

- 沿用/扩展 key：`date`（as-of）、`closed`、`types`、`sec`（既有）+ 新增 `range`/`from`/`to`（日期范围）、`scenario`（场景）。
- 等于默认值不写入 URL（沿用既有规则）；刷新 / 分享后保持。

### 6.3 用户故事

- **US-I05-1**：作为用户，我希望在持仓页只设一次筛选（日期 / 证券 / 场景），持仓、买卖明细、分红费用三块一起变，不用逐板块重复筛选。
- **US-I05-2**：作为用户，我希望「持仓日期卡片」承担统一筛选入口，能快速切换快捷范围、按证券/场景筛选，且刷新页面后筛选不丢。

### 6.4 验收标准

1. 页面顶部只有一个统一筛选器，三板块共享（持仓 / 买卖明细 / 分红费用）。
2. 改变证券筛选 → 三板块同步过滤。
3. 改变场景筛选 → 买卖明细与分红费用同步；持仓板块不受影响（场景控件在持仓语境置灰/隐藏）。
4. 改变日期范围 → 买卖明细与分红费用同步；改变持仓日期(as-of) → 持仓同步。
5. URL 持久化：刷新 / 分享后筛选保持（`date/closed/types/sec/range/from/to/scenario`）。
6. 持仓日期卡片承载新筛选器，原「持仓日期」能力不丢失（默认今日、范围校验、as-of 精确推导）。
7. 三板块各自空状态四态齐全（C-06）；汇总条（`HOLD-B-P0-06`）随筛选动态变化。
8. 与 I-06 联动：卡片内日期范围必须提供快捷范围。

### 6.5 边界情况

- as-of 日期早于所选日期范围 → 持仓按 as-of 精确推导、买卖明细/费用按范围展示，口径差异在 UI 注明。
- 无任何流水时筛选器仍可用，三板块显示空状态 + 清除筛选按钮。
- 证券多选与类型多选叠加 → AND 关系。
- 切换组合 → 筛选重置为默认（沿用既有行为）。
