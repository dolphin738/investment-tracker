## 二、逐项评审

### 2.1 Web 前端 — 评分 8.0/10

| 选型 | 结论 | 说明 |
|------|------|------|
| Vite + React 18 + TS | ✅ 合理 | 工业标准组合。Vite HMR 极快，React 18 LTS 稳定，TS 对金融计算型安全是刚需。 |
| Tailwind + shadcn/ui | ✅ 合理 | 2024-26 最主流的 React UI 方案。基于 Radix 无障碍原语，Dashboard 类应用大量表格/表单/卡片场景生产力极高。 |
| Zustand | ✅ 合理 | 轻量客户端状态管理。配合 TanStack Query 分工明确——后者管服务端缓存，前者只管 UI 内态，角色不重叠。 |
| TanStack Query | ✅ **优秀** | 本栈最佳决策。金融计算（Newton-Raphson 迭代）在后端很重，必须缓存结果避免重复请求。stale-while-revalidate 天然适合"数据可能已过期但不阻塞渲染"。 |
| Axios | ⚠️ 可讨论 | 能工作。JWT 拦截器场景下 Axios 的 interceptor 比裸 fetch 方便，但体积多了 ~13KB gzip。**不算错，非必需而已。** |
| react-hook-form + zod + sonner | ✅ 合理 | 表单方案标准答案。zod 前后端共享 schema 恰好满足 FLOW-P0-05「前端 zod 与后端 DTO 规则完全一致」的硬性要求。 |
| Recharts / ECharts | ⚠️ **有问题** | **同时引入两个图表库是冗余的。** PRD 所有图表场景（净值曲线/XIRR 走势/持仓占比饼图）任选一个都能覆盖。建议二选一：大数据量时序图表优先 ECharts（1800 点 5 年曲线场景更强）。 |

> **小结**：整体是现代主流方案，技术债务低。唯一扣分项是双图表库冗余，应在开发启动前做一次定案。

---

### 2.2 后端 — 评分 9.0/10

| 选型 | 结论 | 说明 |
|------|------|------|
| NestJS | ✅ **优秀** | PRD 有清晰的服务分层（`nav.service` / `xirr.service` / `calculation.service` / `recalculation.service`），NestJS 的 Module/Controller/Service 与之一一对应。内置 Guard/Interceptor 完美支撑 JWT 认证（§9.3）。 |
| Prisma | ✅ 合理 | 型号安全 ORM，migration 成熟。PRD 精度要求（`NUMERIC(18,2)` / `NUMERIC(10,8)`）完全支持。唯一约束映射到 `@@unique` 很自然。注意：复杂聚合走 raw SQL 或 service 层，不走 Prisma 查询。 |
| PostgreSQL 16 | ✅ **优秀** | 金融应用最佳选择。NUMERIC 精度无损、UNIQUE 约束保障 REG-05 每日唯一不变量、事务保证数据一致性。时间序列数据（daily_nav/daily_xirr）天然适合。 |

> **小结**：生产级金融应用标杆组合，无可挑剔。唯一提醒：金融计算逻辑（Newton-Raphson/XIRR/份额法）放 service 层而非 Prisma query 层，这是正确的，确保可测试性。

---

### 2.3 APP 端 — 评分 6.0/10（当前方案：纯 ArkTS）

| 维度 | 评价 |
|------|------|
| 策略 | ✅ PRD 标为 P2、本阶段不交付，策略正确 |
| 生态风险 | ⚠️ 鸿蒙生态仍在成长期，第三方库/社区资源/开发者人才池远小于 RN/Flutter |
| 代码复用 | ❌ **零复用**。Web 用 React + TS，APP 用 ArkTS，`packages/shared` 只能共享类型定义，业务逻辑/状态管理/组件全部重写 |
| 市场覆盖 | ⚠️ 纯鸿蒙 = 放弃 iOS + Android。目标用户为个人投资者时覆盖面偏窄 |

> **小结**：当前方案是 Web 一套 + APP 独立重写，开发成本翻倍、维护两套代码。如果 HarmonyOS 是硬性要求，见第四章替代方案分析。

---

### 2.4 缺失基础设施

PRD 技术栈描述偏"业务代码层"，以下关键项缺失：

| 缺失项 | 为什么重要 | 建议 |
|--------|-----------|------|
| **测试框架** | §10 有 5 条 P0 强制回归测试（REG-01~05），要求「自动化集成测试连真实 PG」 | 后端：Vitest + Supertest；前端：Vitest + Testing Library |
| **CI/CD** | 每次发版前必须完整跑 REG-01~05 | GitHub Actions / 工蜂 CI |
| **日志/监控** | 金融计算异常需要可追溯 | NestJS 内置 Logger + 生产加 Pino |
| **API 文档** | 前后端分离 + 未来 APP 端共用 API | `@nestjs/swagger` 自动生成 OpenAPI |
| **代码规范** | monorepo 多包协作 | ESLint + Prettier 共享配置放 `packages/shared` |

## 三、APP 跨端方案分析

### 3.1 RNOH 作为 APP 替代方案

**RNOH（React Native for OpenHarmony）** 是 RN 在鸿蒙上的原生渲染实现，当前 v0.82.30 稳定版已经生产可用。

#### 对 PRD 的代码复用分析

| 层 | PRD Web 端技术 | RNOH 可复用？ | 共享度 |
|---|---|---|---|
| 类型定义 | `packages/shared` (TS/zod) | ✅ 完全复用 | 100% |
| 状态管理 | Zustand stores | ✅ 完全复用 | 100% |
| 服务端状态 | TanStack Query hooks | ✅ 完全复用 | ~90% |
| HTTP 层 | Axios + JWT interceptor | ✅ 完全复用 | 100% |
| 表单逻辑 | react-hook-form + zod | ✅ 完全复用 | ~95% |
| UI 组件 | shadcn/ui + Tailwind | ❌ 需替换（NativeWind 可桥接） | ~30% |
| 图表 | Recharts/ECharts | ❌ 需替换 | 0% |
| 路由 | React Router | ❌ 替换为 React Navigation | 0% |

**估算整体复用率：40-50%**，而纯 ArkTS 方案是 0%。

#### 代价

- React 版本升级：Web 端需从 18 → 19（RNOH 0.82 已 React 19.1.1）
- shadcn/ui 沉没成本：RN 侧需另选 UI 库（Paper / NativeBase / 自研）
- 鸿蒙特性桥接：分布式数据、原子化服务等仍需写原生 ArkTS 模块
