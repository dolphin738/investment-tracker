# PRD · 系统管理（通用设置模块）

> 版本：v0.1 · 状态：待评审 · 日期：2026-08-12
> 范围：把现有「专属证券行情提供方管理页」重构为**通用的、可扩展的系统管理模块**，证券行情设置仅作为其中一个板块，并新增「接口（输入接口）分类管理」的增删改能力。

---

## 1. 产品目标

一句话：**建设一个可插拔设置模块的系统管理框架，首期落地「证券行情设置」板块，支持按「接入方式（HTTPS / SDK）」划分提供方、并在每个提供方下按接口分类灵活维护输入接口。**

- G1 系统管理页从「专属证券行情页」升级为「通用设置外壳」，板块以注册表方式组织，新增板块零侵入。
- G2 证券行情板块内，提供方先按接入方式（HTTPS / SDK）两大组归类展示，结构清晰。
- G3 每个提供方下可维护多个「输入接口」（A股列表、港股列表、基金列表、可转债列表、A股行情、港股行情、可转债行情等），支持增 / 删 / 改。
- G4 维持现有管理员 RBAC（require_admin）与信封契约不变，向后兼容已有提供方数据。

---

## 2. 用户故事

- **US-1 管理员进入系统管理**：看到左侧「设置模块」列表，当前仅「证券行情设置」一项；点击进入后看到该板块内容。未来加「用户管理」「通知设置」等只需注册新板块，不改外壳。
- **US-2 管理员按接入方式查看提供方**：证券行情板块把提供方分成「HTTPS 提供方」「SDK 提供方」两组，每组内列出提供方卡片/行，并标注默认/当前/禁用状态。
- **US-3 管理员维护某提供方的接口**：展开某提供方，看到其下「接口」列表（按接口分类分组）；可对单个接口进行新增、编辑、删除。
- **US-4 管理员新增一个输入接口**：在指定提供方下点击「新增接口」，选择接口分类（如 A股列表），填写名称、调用路径/方法、请求参数模板、是否启用、备注，保存后生效。
- **US-5 管理员删除/编辑接口**：行内「编辑」回填表单、「删除」二次确认，操作即生效。

## 3. 需求池

### P0（必须，本迭代交付）
- **P0-1 通用外壳**：`admin` 页改为设置模块外壳，含左侧模块列表（数据驱动，当前一项）。非管理员仍展示「无权限访问」且不发请求。
- **P0-2 板块注册机制**：新增设置板块仅需「注册一个 `(key, label, icon, component)`」条目，外壳自动渲染入口与内容区。
- **P0-3 证券板块 · 提供方按接入方式分组**：HTTPS / SDK 两组分别展示；组内保留提供方 CRUD、设为默认/当前、删除（沿用现有能力）。
- **P0-4 接口数据模型**：新增 `quote_provider_interfaces` 表，`provider_id` 外键级联删除，含 `interface_type / name / endpoint / http_method / params(JSON) / enabled / description / 时间戳`。
- **P0-5 接口分类目录**：预置 7 类（见 §5），前端以下拉+「自定义」呈现，后端按字符串存储（可扩展）。
- **P0-6 接口 CRUD 后端**：`/api/admin/quote-providers/{provider_id}/interfaces` 的 list/create，及 `/{interface_id}` 的 update/delete；全程 `require_admin` + 信封。
- **P0-7 接口 CRUD 前端**：在提供方详情/展开区内提供接口子表 + 新增/编辑对话框 + 删除二次确认。

### P1（重要，建议本迭代或紧接）
- **P1-1 接口「启用/禁用」开关**在前端显式呈现并参与保存（后端 `enabled` 已具备）。
- **P1-2 接口参数模板校验**：保存时对 `params` JSON 做基础合法性校验（非空对象 / 可解析）。
- **P1-3 提供方级联**：删除提供方时，其下接口随之删除（DB 级联 + 服务层确认）。

### P2（后续）
- **P2-1 新增第二个设置板块**（如「数据导入映射」「通知渠道」）验证外壳可扩展性。
- **P2-2 接口级「试调」/连通性校验**。
- **P2-3 接口分类支持管理员自定义目录（含图标、排序）**。

## 6. 待确认问题

1. **接口记录字段范围**：本 PRD 取 `interface_type / name / endpoint / http_method / params(JSON) / enabled / description`。是否还需要「超时时间 / 重试次数 / 频率限制」等运行时配置字段？（建议 P2 再加，避免 P0 膨胀）
2. **接口分类形态**：预置 7 类 + 「自定义（自由文本 key）」是否足够？还是希望分类本身也可由管理员在后台配置（即分类表）？
3. **SDK 提供方下的「接口」**：SDK 类提供方是否也用统一的 `endpoint / http_method` 字段（此时 endpoint 可理解为「函数/方法名」），还是 SDK 接口只需「分类 + 名称 + 参数」？建议统一字段、按需留空。
4. **接口是否区分「输入/输出」**：需求只提「输入接口」，是否接口模型需预留 `direction` 字段以便将来扩展输出接口？建议 P0 先不加，结构上不冲突。
5. **权限粒度**：接口 CRUD 是否沿用「仅管理员」即可，还是需要更细的「系统配置管理员」角色？建议沿用 require_admin。

### 6.1 决策记录（2026-08-12 评审）

| # | 待定项 | 决策 | 对 P0 数据模型 / 实现的影响 |
|---|--------|------|----------------------------|
| 1 | 运行时配置字段 | **P0 现在就加**：`timeout`(int, 秒) / `retry_count`(int) / `rate_limit`(varchar) 三列 | `quote_provider_interfaces` 增 3 列；接口 CRUD 表单 + 校验需覆盖 |
| 2 | 接口分类形态 | **预置 7 类 + 自定义文本，且分类后台可配**：新增 `interface_categories` 表，管理员可在后台增删分类（含图标/排序），前端下拉从表读取 | 新增 `interface_categories` 表 + 分类管理 UI；`interface_type` 仍按字符串存，允许自由文本自定义 key |
| 3 | SDK 接口字段 | **统一字段、按需留空**：SDK 与 HTTPS 共用 `endpoint` / `http_method`，SDK 时 endpoint 理解为「函数/方法名」，不用则留空 | 一张表统一建模，无需按接入方式分表 |
| 4 | 接口方向 | **预留 `direction` 字段**：加 `direction`(枚举 in/out) 列，默认 `in` | `quote_provider_interfaces` 增 `direction` 枚举列 |
| 5 | 权限粒度 | **沿用 `require_admin`**：不新增角色 | 接口 CRUD 复用现有管理员守卫 |

> 注：#2 按本轮回选「分类后台可配」理解为**建 `interface_categories` 表、分类后台可配**（与 2026-08-12 早前已回退的那版实现口径一致）；若本意是 P0 不建表，请告知。#1 本轮定为运行时配置三列（timeout/retry_count/rate_limit），与回退版用 `response_mapping` 的口径不同。
