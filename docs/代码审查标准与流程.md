## 0. 目的与定位

### 0.1 现状基线
项目经多轮 AI 协作重写，代码质量**参差不齐**：既有一次性审计（`docs/adr/code-review-2026-08-09.md`）暴露过 XIRR 溢出崩溃（H1）、静默丢数据（M2）、量纲 100× 偏差（M3）等；`docs/archive/代码体检报告-终版.md` 也指出可维护性债（单文件超 400 行、前端边界松弛、测试盲区）。这些**机器静默放行的盲区**需人工审查制度兜底。

### 0.2 定位
本文件定义**人工代码审查**的标准、角色、流程与报告模板。自动化检查（CI 四流水线 + `pre_commit_gate.py`）承担"机器可查项"，本文件承担"机器查不了、必须人看"的项（正确性/数据丢失/需求一致性/安全越权/前端边界/重复垃圾）。**二者互补，非替代。**

### 0.3 零回归原则
既有债务通过 `docs/AI代码清理与瘦身实施计划.md`（cleanup / phase-0，按 REP 编号）逐步收口；**新提交代码须零回归**——不得引入新的 High/Medium 缺陷、不得新增可避免的重复与防御性垃圾。

## 1. 角色与职责（对齐既有三阶提交纪律）

| 角色 | 身份 | 核心职责 | 否决权 |
|---|---|---|---|
| **Engineer**（实现者） | AI agent / 开发 | 实现 → 跑 `pre_commit_gate.py` → 自证 §5 清单 → 按特性拆分提交（Conventional Commits） | — |
| **QA / Reviewer** | CodeReviewExpert 或指定审查者 | 拉真实 diff/读真实代码按 §3/§5 核查 → 出审查报告（§7 模板）→ 列缺陷并分级（§4） | **打回**（发现 P0/P1 未决） |
| **Owner** | senior-dev | 仲裁「一致性 D 类」与架构偏差；裁定最终合入/打回；维护本文件 | **最终否决** |

> 单人项目可由同一人分饰 engineer/QA，但**须切换视角**：自查时按 §5 清单逐项打勾，不得跳过。

## 2. 审查触发时机

| 触发 | 是否强制审查 |
|---|---|
| 推送到 `main` 的 PR（CNB `pull_request`） | **强制** |
| 本地特性/修复提交（尤其 cleanup/phase-0 每轮 REP） | **强制**（逐轮出报告） |
| High/Medium 关键修复、安全相关改动 | **强制** + owner 复核 |
| 架构变更（新增目录/依赖层）、依赖升级（npm/pip） | **强制**（对齐 `AGENTS.md` §1 触发式预读） |
| 纯文档/CRLF 假象（`docs/PRD.md` 类空 diff） | 不审查、不提交 |

## 3. 审查维度（机器盲区为重点）

> 自动化可查项见 §8 分工表；下表「人工必查」为机器静默放行的盲区，**审查者必须逐维过**。

| # | 维度 | 关键检查点 | 依据 |
|---|---|---|---|
| 3.1 | **正确性** | 崩溃型（异常未捕获致事务失败）、**静默丢数据**（多 ID/分页只取首个、集合过滤掩盖）、边界（0/负/极值/空集合/None/除零）、Decimal 精度与量程、事务原子性 | `code-review-2026-08-09` §5 H1/M2/L3 |
| 3.2 | **需求一致性** | 代码 vs `docs/PRD.md` / 方案 / ADR 逐条对照；**冻结不变量不被破坏**（FG/G/C 系列）；无"功能已实现但契约未回传"缺口 | `code-review-2026-08-09` §3/§4 D2 |
| 3.3 | **架构边界** | `import-linter` 4 契约（models 不反向依赖上层、services 不依赖路由层、`core_no_business`）；**前端边界最易漏**（pages/components/composables/api 不得跨层，CI 未 AST 强制，仅 knip 拦导出） | `AGENTS.md` §1；架构治理 §1/§2 |
| 3.4 | **测试** | 改业务源码必带测试（`check_tests_touched`）；**覆盖缺陷场景而非仅 happy path**；CI 覆盖率门槛（finance_core ≥90 / services ≥60 / app ≥70）；盲区判断 | `AGENTS.md` §2；`code-review-2026-08-09` §7 |
| 3.5 | **安全** | 鉴权依赖+查库+软删三层齐全；无 SQL 字符串拼接；跨用户 `user_id` 过滤不可绕；枚举/权限校验不靠前端隐藏 | `code-review-2026-08-09` §5 C-09 |
| 3.6 | **可维护性** | 单文件 ≤400 行（人工约定，CI 不拦）；函数单一职责（§5）；**无防御性垃圾**（异常后静默返默认、无意义重试包裹）；**无重复块**（相似度 ≥0.9 的复制粘贴）；无死代码/死导出（knip 兜底） | `AGENTS.md` §1/§4；pre_commit_gate 清单 |
| 3.7 | **性能与体积** | 无 N+1（循环查库）；前端 bundle 不超 `scripts/bundle-baseline.json` 基线；大对象不进循环 | `AGENTS.md` §2；架构治理 §8 |

## 4. 严重度分级（对齐既有 H/M/L + 一致性 D）

| 级别 | 符号 | 定义 | 合入处置 |
|---|---|---|---|
| **P0 / High** | 🔴 | 崩溃型缺陷、数据丢失、安全越权、冻结不变量破坏 | **阻塞**，须立即修，修复前不得合入 |
| **P1 / Medium** | 🟠 | 功能语义偏差（量纲/契约/口径）、部分数据错误 | **阻塞**，须修或 owner 书面豁免 |
| **P2 / Low** | 🟡 | 边界/健壮性缺口、可维护性小问题 | 排期修，不阻塞 |
| **一致性 D** | ⚠️ | 代码 vs 文档/需求/ADR 的**偏差或歧义**（含已澄清的误报） | 须 owner 裁定：要么改代码、要么更新文档，**不得"已知偏差"悬而不决** |
| **债务** | 🔧 | 历史遗留、非本次引入、由 cleanup REP 收口 | 登记 backlog，不阻塞本次合入（零回归即可） |

> 命名约定：**H/M/L 用于"功能缺陷"**，**D 用于"文档/需求一致性"**，二者独立计数。

## 5. 审查清单（Checklist · 提交人自证 + 审查者逐条核验）

```
── 正确性（3.1）──────────────────────────────
  □ 单路径失败不污染整段事务（try/except 局部化，参照 H1）
  □ 无静默丢数据（多 ID/分页/集合过滤后是否仍全量，参照 M2）
  □ 边界值已覆盖：0、负、极值、空集合、None、除零
  □ Decimal 精度/量程正确（落库前量程保护，参照 H1）
── 需求一致性（3.2）──────────────────────────
  □ 逐条对照 PRD/方案：✅已实现 / 🟡部分 / ⚠️不一致 / ❌未实现
  □ 冻结不变量（FG/G/C）零破坏
  □ 契约响应体完整（如重算须回传 recalculatedDays，参照 D2）
── 架构边界（3.3）────────────────────────────
  □ import-linter 4 契约通过（CI 拦）
  □ 前端边界无跨层（pages→components→composables→api 方向，最易漏）
  □ 无新增依赖；或已在提交说明写"为何现有能力做不到"（§3 准入）
── 测试（3.4）────────────────────────────────
  □ 改业务源码必带测试（check_tests_touched 告警）
  □ 测试覆盖缺陷场景（非仅 happy path），非"为绿而绿"
  □ CI 覆盖率门槛达标（finance_core≥90/services≥60/app≥70）
── 安全（3.5）────────────────────────────────
  □ 鉴权：依赖+查库+软删三层齐全
  □ 无 SQL 拼接；跨用户 user_id 过滤不可绕
── 可维护性（3.6）────────────────────────────
  □ 单文件 ≤400 行（大文件须拆分或 owner 裁定）
  □ 函数单一职责；无防御性垃圾；无复制粘贴（相似度≥0.9）
  □ 本次提交只做一件事（功能/重构/格式化不混排）
──────────────────────────────────────────────
```

## 6. 审查流程（时序）

```
① Engineer  实现 → 跑 pre_commit_gate.py → 自证 §5 清单 → 按特性 Conventional Commits 提交
      │
② QA        拉 diff / 读真实代码（禁止凭记忆/文档推断）→ 按 §3/§5 核查
      │       → 出审查报告（§7 模板）→ 列缺陷并分级（§4）
      │
③ Owner     仲裁 D 类一致性项 + 架构偏差 → 裁定合入 / 打回
      │
④ Engineer  按分级修（P0/P1 立即；P2 排期）→ 再走 ②→③
      │
⑤ 合入      push main（dev-scripts/push-all.ps1 + CNB_TOKEN，勿直推）
      │       → 合并后从构建页核验 CI 四流水线（#001 backend-lint / #002 frontend-lint
      │         / #003 backend-test / #004 frontend-test；CNB statuses 不阻塞，须看构建页）
      │
⑥ 归档      审查报告**终稿**落 `docs/reviews/`（命名 review-<模块>-<轮次>-<日期>.md，
            目录不存在则新建）；会话内即时草稿可暂存 `.workbuddy/artifacts/`，
            合入前须归档到 `docs/reviews/`（避免散落 artifact 区无法检索）
```

> **信任但核实（trust but verify）**：QA 须核对 engineer 自述与 `git status`/`git diff`；核实测试是否真覆盖缺陷场景，而非仅语法绿。

## 7. 审查报告模板（对齐 `code-review-2026-08-09.md` 风格）

```markdown
# 代码审查报告 · <模块/主题>（<日期>）

## TL;DR
一句话结论（✅ 通过 / 🔴 打回）+ 缺陷计数（P0×? P1×? P2×? D×?）。

## 关键判断澄清
| # | 原假设/旧记忆 | 代码事实（file:line） | 处置 |
|---|---|---|---|

## 缺陷清单（按严重度，附证据链）
### 🔴 P0/High
- **H1 · <标题>**：位置 `<file>:<line>`；现象；阈值；修复建议。
### 🟠 P1/Medium …  🟡 P2/Low …  ⚠️ D 类一致性（含误报标注）

## 测试盲区
（改了源码却未覆盖的风险路径，逐条列出）

## 验证结果
- 后端 pytest <N passed> ｜ 前端 vitest <N passed> ｜ vue-tsc 0 错
- ruff / import-linter(4 contracts) / knip 全过

## 决议与下一步
owner 裁定项 + 待办（含 cleanup REP 登记项）。
```

> 每条结论**必须带 `file:line` 证据链**，禁止"看起来没问题"式空述。

## 8. 人机分工（自动化 vs 人工）

| 检查项 | 自动化（CI + pre_commit_gate） | 人工（QA 必查） |
|---|---|---|
| ruff / import-linter / knip / 行数 / 体积 | ✓ 强制 | 复核误报 |
| 后端/前端覆盖率门槛 | ✓ CI 强制 | 盲区判断（§3.4） |
| 正确性 / 静默丢数据 / 边界 / 事务 | ✗ | ✓ **必查**（§3.1） |
| 需求一致性 / 冻结不变量 | ✗ | ✓ **必查**（§3.2） |
| 安全越权 / SQL 注入 | 部分（auth 装饰器） | ✓ **必查**（§3.5） |
| 单一职责 / 防御性垃圾 / 重复块 | ✗ | ✓ **必查**（§3.6） |
| 前端边界（CI 未 AST 强制） | ✗ | ✓ **最易漏，重点**（§3.3） |

## 9. 通过门槛

1. **自动化闸门全绿**是合入**必要非充分**条件。
2. **零 P0/High、零 P1/Medium 未决** → 可合入。
3. **D 类一致性项须 owner 裁定**：即使"文档过时"也要更新文档或代码，不得悬而不决。
4. **债务项**不阻塞本次合入，但须登记 `docs/backlog.md` 或对应 cleanup REP。
5. 报告模板（§7）缺失或证据链不足 → 打回补正。
