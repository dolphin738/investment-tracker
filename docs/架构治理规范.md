## 1. 目录职责与禁止事项（§4.1-1）

### 1.1 后端 `backend/app/`

| 目录/文件 | 职责（一句话） | 禁止事项 |
| --- | --- | --- |
| `modules/` | API 路由层：参数校验、权限依赖、调用 service、分页 | 禁止写业务计算逻辑；禁止直接绕过 service 改 ORM 数据 |
| `services/` | 业务逻辑层：领域规则、跨实体编排、重算触发 | 禁止 import `app.modules`（路由层）；禁止构造**他域** ORM 模型（AST 检查） |
| `finance_core/` | 纯函数计算内核（xirr / nav / holding） | 禁止 import DB / ORM / HTTP / 配置；只做纯计算 |
| `models/` | ORM 表模型与枚举 | 禁止 import services / modules（不反向依赖上层） |
| `core/` | 横切关注：security(JWT/bcrypt)、envelope、exceptions、enums、config | 禁止 import 业务层（services/modules/models） |
| `db/` | 引擎/会话/基类 | 禁止承载业务逻辑 |
| `schemas.py` / `schemas_resp.py` | 请求 DTO（*Req）/ 响应 DTO（*Out） | 禁止塞业务逻辑；金额统一 DecimalStr |
| `serializers.py` | ORM 实体 → camelCase 响应 dict 纯函数 | 禁止访问 DB；禁止依赖路由层 |
| `storage/` | 文件/上传存储 | 禁止 import 业务层 |
| `main.py` | 应用装配、路由注册、lifespan | 禁止写业务逻辑；字面路由须先于参数路由注册 |

### 1.2 前端 `web/src/`

| 目录 | 职责（一句话） | 禁止事项 |
| --- | --- | --- |
| `api/` | HTTP 接口定义（axios 封装 + 各域 .api.ts） | 禁止写业务逻辑与组件状态；禁止 import components/modules |
| `composables/`（各模块内） | 该模块的状态编排/查询封装（vue-query） | 禁止直接操作 DOM；禁止互相跨模块 import |
| `modules/<域>/pages|components/` | 页面与展示组件 | 禁止绕过 api 层直接发 HTTP；展示组件禁止直接调 API（走 composable/api） |
| `components/` | 跨模块通用展示组件（含 charts） | 禁止 import 任何 `modules/*` |
| `router/` | 路由与守卫 | 守卫只做鉴权/重定向，禁止写业务 |
| `stores/` | Pinia 全局状态 | 禁止放服务端数据的权威副本（服务端数据走 vue-query） |
| `lib/`、`constants/`、`types/`、`composables/` | 共享工具/常量/类型/全局组合式 | 单向依赖：components/modules → lib 等，禁止反向 |
| `types/api.ts` | **生成物**（`web/scripts/gen-api-types.py` 产出） | **禁止手改**；改后端契约 → 重新生成 |

> 边界的自动化现状：后端反向依赖由 `backend/.importlinter` + `tests/test_arch_boundaries.py`（AST）强制；
> 前端边界为约定 + knip 文件/依赖检测，尚未 AST 强制（见 §6 后续项）。

## 2. 调用边界（依赖方向，§4.1-2）

```
后端： modules(routers) ──▶ services ──▶ models / finance_core
                                   ▲              │
        core ◀─────────────────────┴──────────────┘   （任何层都可 import core）
        禁止：models ─▶ services/modules；services ─▶ modules；finance_core ─▶ 任何 DB/HTTP

前端： pages / components ──▶ composables ──▶ api ──▶ (axios)
        components(通用) ╳─▶ modules/*；types/api.ts 只读生成
```

## 3. 新增依赖准入（§4.1-3 + §4.3-2）

1. 新增任何依赖（Python / npm）必须在 PR/提交说明中回答：**「为什么现有依赖/原生能力做不到」**。
2. 前端由 knip 闸门强制：新增未使用依赖直接 fail（`web/knip.json`，CI `knip --include dependencies,unlisted,files`）。
3. Python 依赖一律**钉死版本**进 `backend/pyproject.toml`（现行为先例）；可选/懒加载依赖（akshare、apscheduler）注明用途。
4. 依赖总数相对 main 增加超过 3 个时须在 PR 说明整体理由。
5. 已知豁免（knip `ignoreDependencies`）：`postcss-load-config`——postcss 生态传递依赖，postcss.config.js 间接使用，声明入库需动 pnpm-lock，豁免并在此记录。

## 4. 文件行数上限（§4.1-4）

- **新文件 ≤ 400 行**，超限需在提交说明中给出拆分理由。
- **存量超限文件禁止继续增长**：改动时鼓励顺带拆分；大拆（>100 行位移）单独立轮，不混入功能提交。
- 现存超限大户（阶段 4 时点基线，供后续瘦身参考）：
  `app/services/market_data_sync.py`(1146)、`app/modules/admin/router.py`(829)、
  `web/src/types/api.ts`(1021，生成物不适用)、`web/src/modules/admin/pages/SchedulePage.vue`(902)、
  `web/src/modules/settings/pages/SettingsPage.vue`(884)、`DashboardPage.vue`(775)。

## 5. 函数职责（§4.1-5）

- 一个函数只做一件事；禁止在既有函数里「顺手」加功能——新用途 = 新函数。
- 路由 handler 只做「校验→调 service→序列化返回」三段；复杂分支下沉 service。

## 7. 任务微型化纪律（§4.2）

大任务必须拆成多次小步对话/提交，每步只做一件事、可独立验证。示例：

- ✗ 错误：「给行情模块加稳定性保障」（重试+限流+超时+监控混一步）
- ✓ 正确：
  1. 只加 `_fetch_https_raw` 的超时参数，跑 `pytest -k resilience`；
  2. 只加重试（指数退避），补单测；
  3. 只加按接口 id 的限流，补单测；
  4. 同步状态暴露到 sync-status 端点，补端点测试。

## 8. 提交自动检测流程（§4.4）

每次 AI 生成代码提交前执行：

```bash
python scripts/pre_commit_gate.py            # 全量（ruff + import-linter + knip + 行数预算）
python scripts/pre_commit_gate.py --skip knip  # 离线快速模式
```

- 自动项（任一不过即打回）：新增 export 至少一处使用（knip）、未使用依赖/文件（knip）、
  未使用 import/变量（ruff F）、架构边界（import-linter）、行数预算（>800 需 `LARGE_PR_APPROVED=1` 人工豁免）。
- 人工项（脚本打印清单，提交人自证）：依赖准入说明、防御性垃圾（吞异常返回默认值/无意义重试/相似度 ≥0.9 复制块）、单一职责拆分。
- 测试仍按项目工作流单独跑（后端 `uv run pytest`、前端 `vitest run` + `vue-tsc`），闸门不替代全量回归。
