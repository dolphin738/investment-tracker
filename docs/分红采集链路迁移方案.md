# 分红采集链路迁移方案：公告探测 + 巨潮历史分红

> 状态：**待评审**（本轮只出方案，未改任何业务代码）
> 创建：2026-09-19
> 范围：淘汰东财批量季报抓取与新浪逐股分红补充/回补，改为「cat 4 公告探测 → 命中证券按代码调巨潮 `stock_dividend_cninfo` 拉全量历史分红」

---

## 0. TL;DR

| 项 | 结论 |
|---|---|
| 新数据源是否可用 | **是**。实测 5 只标的（含沪市/深市/创业板）全部成功，单只返回 13~31 行全历史分红，单只耗时约 0.5~1.3s |
| 能否复用现有「公告探测」环节 | **能，且几乎零改动**。`DIVIDEND_NOTICE_SCAN` 的 `scan()` 已是「一次拉全市场公告 → 本地标题二筛 → 得到命中证券」的形态，只需把第二步的数据源从新浪换成巨潮 |
| 配置是否需要改代码 | **否**。`stock_dividend_cninfo` 当前已在 cat 3「股息列表」且 `params` 含 `symbol`，正好满足 `dividend_detail_source_interface_id` 的校验（cat 3 + `require_per_symbol=True`），管理端切一下即可 |
| 主要工作量 | 重写 `_process_master` 的解析层（新浪 4 列硬编码 → 巨潮配置化取值）+ 删除清单（约 15 处符号、1 个路由、1 个 JobType、1 个迁移、5 处前端） |
| 最大风险 | ① **限流预算**：接口 `rate_limit=10/min`，全市场 11430 只需约 **19 小时**，首次全量不可硬跑；② **口径冲突**：新旧行的 `report_year/quarter` 推导不同，可能导致同一笔分红并存两行、股息率重复计数 |

## 1. 现状：三条采集合力 vs 新方法

### 1.1 现有入库链路（A 类采集）

| # | 链路 | 入口 | 数据源 | 每次获取范围 |
|---|---|---|---|---|
| ① | 季度股息抓取 | `DIVIDEND_QUARTERLY_FETCH` → `dividend_sync.py:150 quarterly_fetch` | cat 3 批量源 `d48eb92b…`（东财，`date=YYYYMMDD`） | 某报告期全市场一行一条，**需按时序逐个报告期抓** |
| ② | 公告扫描后逐股补充 | `DIVIDEND_NOTICE_SCAN` → `dividend_notice_scan.py:228 scan` → `_process_master:385` | cat 3 明细源 `34249dca…`（新浪 `stock_history_dividend_detail`） | **按 symbol 逐只**查，返回该股分红记录 |
| ③ | 特别分红历史回补 | `POST /dividend-yield/backfill-specials` → `_backfill_one:656` | 同上新浪源 | 逐只回补最近 5 个财年 |

### 1.2 新方法

```
cat 4 公告源 stock_notice_report（一次调用，拉全市场当日公告）
        │ 标题二筛：分红|派息|权益分派|利润分配|分配方案
        ▼
命中的证券代码集合
        │ symbol = 纯数字代码
        ▼
stock_dividend_cninfo（按股调用）→ 该股**全部历史分红**（实测 13~31 行）
        │ 映射 + upsert
        ▼
security_dividends
```

**关键差异**：巨潮一次调用即返回该股**全历史**（含年度/中期、送转派），因此同时覆盖了链路①（历史报告期）与链路③（特别分红回补）的能力，这两条在功能上是冗余的。

## 2. 为什么旧方法可以淘汰（实证）

1. **覆盖面已被实证超越**：实测 `600519`=31 行、`000001`=29 行、`601398`=22 行、`000858`=28 行、`300750`=13 行，均含完整历史，不需要再按报告期逐个抓取（链路①的动机消失）。
2. **回补机制失去意义**：`backfill_specials`（链路③）存在的前提是「单次抓取拿不到历史」；巨潮天然全历史，回补按钮成为只带来重复写入风险的负担。
3. **新浪源维护成本高**：`dividend_notice_scan.py:67-75` 硬编码 4 个新浪列名，且 `:70-71` 注释已自陈「无机代码列、历史占位」，属长期技术债。
4. **并行期是有害的**：①/③ 与新方法并存会产生两套不同 `period_type`/`(ry,rq)` 口径的行（详见 §6），股息率会重复计数。

## 5. 新方法落地设计

### 5.1 第一步：配置切换（零代码，可立即执行）

管理端 → 股息率全局设置 → **分红明细源** 改为 `巨潮-历史分红`（`d089591d-5a84-48d1-b5d2-ba9c1b94a730`）。

已核实满足 `settings_router.py:163` 的两条校验：

- `category_id == '3'`（股息列表）✅
- `require_per_symbol=True` → `params` 含 `symbol` 键 ✅（`{"symbol":"600009"}`）

> 附带一处提醒：该接口现在被绑了一个 `code` 槽，`source="code"`，但巨潮响应**并不存在** `code` 列（响应 11 列全为分红字段）。由于该字段 `required=false`，且本链路的证券代码来自**调用方传入的 symbol**而非响应行（见 §5.2），运行时不会因此中断。此绑定建议保留——它是满足 cat 3 slot 契约（`response_fields.py:72-77`）所必需的占位，删掉会导致配置校验不通过。

### 5.2 第二步：调用编排（改造 `_process_master`）

```python
digits = re.sub(r"\D", "", code)          # sh600519 → 600519，逻辑不变
params = {**(detail.params or {}), "symbol": digits}
rows   = await self._mds.call_interface_raw(detail, params, None)   # 返回该股全历史
```

- 证券代码取自函数调用参数，不依赖响应行的 code 槽（与现有新浪路径口径一致）。
- 遍历**全部返回行**（不再是「取当天那一条」），逐行映射 upsert。
- 保留现有「按证券独立 commit、单只失败 rollback 后继续」的容错结构（`scan():291`），以及末尾 `refresh_yields_for_masters` 重算（`:307`）。

### 5.3 字段映射表

`SecurityDividend`（表 `security_dividends`，唯一键 `uq_security_dividends_master_period(master_id, report_year, report_quarter, period_type)`）：

| 目标列 | 巨潮源列 | 转换 |
|---|---|---|
| `cash_per_share` | 派息比例 | `Decimal(值) / 10`（每 10 股 → 每股）；空/NaN → 跳过该行 |
| `ex_dividend_date` | 除权日 | `core.date_utils.parse_date` |
| `record_date` | 股权登记日 | 同上（该列已存在：`models/dividend_yield.py:90`） |
| `announcement_date` | 实施方案公告日期 | 同上 |
| `report_year` / `report_quarter` | **报告时间** | 「2024年报」→ (2024, 4)；「2025半年报」→ (2025, 2)；一/三季报 → (Y, 1/3) |
| `period_type` | 分红类型 | 「年度分红」→ `ANNUAL`；「中期分红」→ `INTERIM`；其余 → `QUARTERLY` |
| `status` | — | 除权日非空 → `PAID`；否则 `PROPOSED`（见 §5.4） |
| `source` | — | `detail.name` |

> 未使用：`送股比例` / `转增比例` / `派息日` / `股份到账日` / `实施方案分红说明`。当前模型无对应列；若后续要支持送转，需扩表（属新需求）。

### 5.4 两处语义缺口（必须显式定义）

1. **`report_year/quarter` 推导口径变更**：旧 `_anchor`（`dividend_notice_scan.py:83-88`）用**公告日期**的年月推季度；巨潮直接给出**报告期**。必须改用报告期解析，否则同一笔分红会算出与旧行不同的 `(ry, rq)`。
2. **`status` 无源可依**：新浪有「进度」列（`"实施" in progress`），巨潮**没有**。建议规则：**除权日非空 → `PAID`，否则 → `PROPOSED`**。副作用是历史行（已除权）会一律落 `PAID`，这在语义上是正确的。

### 5.5 公告探测环节的必要放宽

`_classify_notices:366-369` 当前判定为：

```
candidate = 命中分红 ∧（标题含「特别」或「中期」）
cancel    = 命中分红 ∧（标题含「取消」或「终止」）
两者皆否 → 直接丢弃
```

即**普通年度分红公告（标题无「特别/中期」）不算命中**，这在旧链路下是为了避免向新浪发过多请求；新方法下会漏掉年报分红。

**建议**：`candidate` 放宽为「命中分红正则 ∧ 非 cancel」，并保留原「特别/中期」标记用于 `period_type` 兜底提示。改前需同步改单测（`test_dividend_notice_scan.py` 的标题二筛用例）。

### 5.6 幂等与去重

- 唯一键 `(master_id, report_year, report_quarter, period_type)` 天然保证重复运行不产生重复行 → 按 `report_year/quarter/period_type` 定位后**更新**金额与日期，不存在则插入。
- 保留 `_westward_dup`（同 master 同 `ex_dividend_date` 或 `(ry,rq,cash)` 全等则跳过）作为二次护栏。

## 6. 存量数据迁移（**不做会有重复计数**）

旧链路写入的行是 `period_type=SPECIAL` + `_anchor(公告日)` 推出的 `(ry,rq)`；新链路写 `ANNUAL/INTERIM` + 报告期推出的 `(ry,rq)`。两者不满足同一个唯一键，**同一笔分红会并存两行**，`consecutive_years`/`compute_yield` 会重复累加。

建议随同一迁移执行（需你确认口径）：

```sql
-- 删除由新浪源写入的历史行，交由巨潮重新灌入
DELETE FROM security_dividends
WHERE source = '新浪-分红配股';   -- 以存量行的实际 source 值为准，执行前先 SELECT 核对条数
```

执行顺序：**先切换配置 → 跑一轮新采集 → 核对新行数 ≥ 旧行数 → 再删旧行**。不可先删后采。

| 单只调用耗时 | 0.5~1.3s | 实测 5 只，累计 6.07s |
