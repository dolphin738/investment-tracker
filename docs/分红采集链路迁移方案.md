## 1. 现状：三条采集合力 vs 新方法

### 1.1 现有入库链路（A 类采集）

| # | 链路 | 入口 | 数据源 | 每次获取范围 |
|---|---|---|---|---|
| ① | 季度股息抓取 | `DIVIDEND_QUARTERLY_FETCH` → `dividend_sync.py:150 quarterly_fetch` | cat 3 批量源 `d48eb92b…`（东财，`date=YYYYMMDD`） | 某报告期全市场一行一条，**需按时序逐个报告期抓** |
| ② | 公告扫描后逐股补充 | `DIVIDEND_NOTICE_SCAN` → `dividend_notice_scan.py:228 scan` → `_process_master:385` | cat 3 明细源 `34249dca…`（新浪 `stock_history_dividend_detail`） | **按 symbol 逐只**查，返回该股分红记录 |
| ③ | 特别分红历史回补 | `POST /dividend-yield/backfill-specials` → `_backfill_one:656` | 同上新浪源 | 逐只回补最近 5 个财年 |

### 1.2 新方法

```
cat 4 公告源 stock_notice_report（一次调用，拉全市场当日公告）
        │ 标题二筛：分红|派息|权益分派|利润分配|分配方案
        ▼
命中的证券代码集合
        │ symbol = 纯数字代码
        ▼
stock_dividend_cninfo（按股调用）→ 该股**全部历史分红**（实测 13~31 行）
        │ 映射 + upsert
        ▼
security_dividends
```

**关键差异**：巨潮一次调用即返回该股**全历史**（含年度/中期、送转派），因此同时覆盖了链路①（历史报告期）与链路③（特别分红回补）的能力，这两条在功能上是冗余的。

## 2. 为什么旧方法可以淘汰（实证）

1. **覆盖面已被实证超越**：实测 `600519`=31 行、`000001`=29 行、`601398`=22 行、`000858`=28 行、`300750`=13 行，均含完整历史，不需要再按报告期逐个抓取（链路①的动机消失）。
2. **回补机制失去意义**：`backfill_specials`（链路③）存在的前提是「单次抓取拿不到历史」；巨潮天然全历史，回补按钮成为只带来重复写入风险的负担。
3. **新浪源维护成本高**：`dividend_notice_scan.py:67-75` 硬编码 4 个新浪列名，且 `:70-71` 注释已自陈「无机代码列、历史占位」，属长期技术债。
4. **并行期是有害的**：①/③ 与新方法并存会产生两套不同 `period_type`/`(ry,rq)` 口径的行（详见 §6），股息率会重复计数。

### 5.2 第二步：调用编排（改造 `_process_master`）


### 5.4 两处语义缺口（必须显式定义）

1. **`report_year/quarter` 推导口径变更**：旧 `_anchor`（`dividend_notice_scan.py:83-88`）用**公告日期**的年月推季度；巨潮直接给出**报告期**。必须改用报告期解析，否则同一笔分红会算出与旧行不同的 `(ry, rq)`。
2. **`status` 无源可依**：新浪有「进度」列（`"实施" in progress`），巨潮**没有**。**裁决规则（2026-09-20 已采纳，§9.3-A2）**：**除权日非空 → `PAID`，否则 → `PROPOSED`**。副作用是历史行（已除权）会一律落 `PAID`，这在语义上是正确的。

### 5.5 公告探测环节的必要放宽

`_classify_notices:366-369` 当前判定为：

```
candidate = 命中分红 ∧（标题含「特别」或「中期」）
cancel    = 命中分红 ∧（标题含「取消」或「终止」）

```

即**普通年度分红公告（标题无「特别/中期」）不算命中**，这在旧链路下是为了避免向新浪发过多请求；新方法下会漏掉年报分红。

**建议**：`candidate` 放宽为「命中分红正则 ∧ 非 cancel」，并保留原「特别/中期」标记用于 `period_type` 兜底提示。改前需同步改单测（`test_dividend_notice_scan.py` 的标题二筛用例）。

- 直连 akshare（`webapi.cninfo.com.cn` 主机）顺序突发 **15 次 / 约 34s（≈26/min）**，结果 **15/15 成功、0 失败、无 429、无封禁**，单只 0.46~6.8s。

> `stock_dividend_cninfo` 实调抛 `KeyError: 'records'`（与本节 2026-09-19 的「15/15 成功」不一致），已定性的链路与结论：

### 9.1 Q6 口径说明：送转不进收益率，改按「除权复权重述」（2026-09-20 修订）

> **修订说明**：本节原裁决为「送转并入综合股息率（方法 A：`total_yield = cash_yield + bonus_yield`）」，
> 经外部佐证复核后**推翻**，改为下述口径。依据见下。

**结论**：送股 / 转增是**股票股利**，除权除息后股价按同比例下调，股东总财富不变（市值中性）。
因此送转**不产生现金收益、也不进收益率**；它要做的是对**历史每股分红做股本口径重述**，否则会造成系统性高估。

**佐证**（雪球《基础知识：股息率的算法（二）》，实例 万盛股份 SH603010，方案「10 转 4 派 4」）：

| 时点 | 每股分红 | 股价 | 股息率 |
|---|---|---|---|
| 除权前 2021-04-26 | 0.4（转增不额外发现金） | 26.97 | **1.48%** |
| 除权后 2021-04-27 | 4 元 / 14 股 = **0.2857** | 19.09 | **1.497%** |

原文两个要点：

1. 「不会因为预案中有转增股份，就多分给你几元」——分红按**旧股本**盘子宣告，转增不产生额外现金；
2. 「除权除息日之后，要加上所送转的股份来计算每股分红」——10 股变 14 股后，历史每股分红须按**新股本**重述。

分子（每股分红）与分母（股价）**同比例下降**，股息率基本不变（1.48% → 1.50%，残差来自现金出表与市场噪声）。
这正是「市值中性」的直接验证。

**为什么推翻方法 A**：方法 A 把「每股多得 b 股」直接加成收益率，本质是把股数增加当成收益，
却未扣除对应的股价稀释 → 对高送转个股**系统性虚增**。按上例它会给出 `0.4/19.09 + 0.4 ≈ 42%` 的荒谬值，
正解是 `1.497%`。更糟的是它掩盖了 §9.2 的真实缺口：该修的分子没修，反倒多算一笔不存在的收益，属重复计算。

**目标口径：除权复权重述（待实现，不进 P0）**

对进入 TTM / LFY 窗口的每笔现金分红 `i`，按其自身 `ex_dividend_date` 之后发生的**所有**送转事件 `j`
（含同一方案同时除权的送转，即 `j.ex_date >= i.ex_date`，且 `j.ex_date <= 计算基准日`）累乘缩股因子重述分子：

```
b_j = bonus_share_ratio_j + convert_ratio_j        # 每股送转股数（源「每 10 股」已 ÷10）
cash_adj_i = cash_per_share_i / Π_j (1 + b_j)      # 重述到「当前股本」基准
股息率     = Σ_i cash_adj_i / price                # price = 最新不复权收盘价，已是当前股本基准
```

- 分子分母同为**当前股本基准**，相除还原为真实现金股息率，**不虚增**；
- 未来才除权的送转（`j.ex_date > 基准日`）不参与——彼时股价仍是旧股本基准；
- 万盛验证：`0.4 / (1 + 0.4) = 0.2857` → `0.2857 / 19.09 = 1.497%` ✓ 与原文一致；
- 累乘天然覆盖**多次累计送转**，弥补原文只讲单次除权的局限。

**对既有裁决的影响**：

| 项 | 处置 |
|---|---|
| `bonus_share_ratio` / `convert_ratio` 两列（迁移 `0030`） | **保留**——用途由「加进收益率」改为「复权重述因子 + 方案展示」（§5.3.1 消费侧 #2 已同步） |
| `compute_yield` 的 `numerator` / `dividend_yield` | **仍只计现金**，语义不变；`YieldResult` 不再新增 `bonus_yield` / `total_yield` |
| 快照 / 曲线 / rankings 默认排序 | 维持现金口径，`user_preferences` 阈值 0.05 / 0.03 不受影响；原悬而未决的「综合排名是否改用 `total_yield`」随之消解 |
| `consecutive_years` / `has_recent_dividend`（送转-only 行） | **2026-09-20 裁决：不计入**（§9.3-A1）。纯送转行不落库 → 计数天然不含；`_PAYABLE` 不动，**零改动** |

### 9.2 已识别缺口（本次不实现）：送转除权后的分子 / 分母基准错配

**代码核实结论**（2026-09-20 全仓 grep）：目前**不存在任何复权 / 重述逻辑**。

| 事实 | 证据 |
|---|---|
| 分母 = 最新**不复权**收盘价（已是「当前股本」基准） | `services/dividend_yield.py:7`、`services/dividend_yield_refresh.py:50` |
| `cash_per_share` = 方案宣告口径（**旧股本**基准，「每 10 股派 X 元」÷10） | `models/dividend_yield.py:79-80` |
| 尚无 `bonus_share_ratio` / `convert_ratio` 列，**无法感知送转** | `models/dividend_yield.py` 的 `SecurityDividend`（2026-09-20 现状仅 `cash_per_share`） |

**后果**：某股发生送转后，只要该笔分红仍在 TTM / LFY 窗口内，计算即退化成
「**旧股本分子 ÷ 新股本股价**」，股息率被高估约 **`(1 + 送转率)`** 倍，直至该笔分红滚出窗口。

以 §9.1 的万盛数据复算：

| 算法 | 计算 | 结果 |
|---|---|---|
| 朴素（当前代码等价） | `0.4 / 19.09` | **2.096%**（高估 ×1.4） |
| 复权重述（目标口径） | `0.4 / 1.4 / 19.09` | **1.497%** ✓ |

**修复要点（待排期）**：按 §9.1 公式重述分子。注意重述**需要跨行的送转信息**，
无法塞进逐行的 `to_cell`，应在 `services/dividend_yield.py` 增加一个窗口级辅助函数
（如 `restated_cells(records, as_of)`），由快照与曲线**两个调用方共用**，避免两处口径分叉。
