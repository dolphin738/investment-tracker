### 2.1 由 D-01 ~ D-05 推导出的三条边界（架构师必须严格遵守）

> 这三条边界是把用户口语化的决策翻译成工程约束，是本次修订的核心。写不清架构师一定会做错。

#### 边界 1：持仓与计算引擎的隔离，是「无自动联动」，不是「物理隔绝」

这是本次最容易被实现错的一点，请逐字理解：

- **收益计算引擎（`nav.service.ts` / `xirr.service.ts`）的唯一输入，仍然是 `AssetSnapshot.totalAsset` 与 `Transaction`。**
- **持仓表（`HoldingSnapshot` / `HoldingPosition`）、分红记录、费用记录，永远不会被计算引擎读取。** 计算引擎的任何查询语句中都不得出现这三张表。
- 但「一键同步」是**用户显式发起的一次写操作**：它把持仓侧算出的合计值**写进** `AssetSnapshot.totalAsset`。写入完成之后，计算引擎读到的仍然是**那条资产快照**，而不是持仓表。

> 🔑 **一句话钉死**：**持仓数据不喂给计算引擎，只有用户点了「同步」把数字抄进资产快照，计算才会因为「快照变了」而触发——触发源永远是资产快照，不是持仓。**
>
> ⛔ **反面案例（严禁实现）**：在 `HoldingSnapshot` 的 save / update 钩子里调用 `triggerCalculation` 或 `recalculateFromDate`。**持仓保存本身绝不触发任何 NAV / XIRR 计算。**

#### 边界 2：现金余额是持仓快照上的一个手工字段

- 用户每次录入/更新持仓快照时，除各标的的数量与市值外，**单独手工填写一个现金余额**。
- 持仓模块的展示口径：**`组合总市值 = Σ 各标的市值 + 现金余额`**。
- 该「组合总市值」是**持仓模块自己的展示值**，与 `AssetSnapshot.totalAsset` 是**两个独立的数字**，除非用户主动同步，否则互不影响。

#### 边界 3：一键同步与手动录入并存，二选一，不强制、不互斥

- 用户既可以点「一键同步」（把持仓合计写入当日资产快照），也可以照旧去快照页手动输入。**两条路都必须保留**，不得因为引入同步就废掉手动录入。
- 持仓合计与当日已有资产快照不一致时：**只展示差异 + 提供一键同步按钮，不做强制校验、不阻塞任何操作**。
- 完整的场景定义（覆盖策略 / 日期对应 / 重算范围 / 反馈形式）见 **§4.8**，架构师请勿自行推测。

### 2.2 全局约束（所有模块必须遵守）

| 编号 | 约束 | 说明 |
|------|------|------|
| C-01 | **金融计算全部在后端** | 前端只做格式化展示，禁止在 React 侧计算 XIRR、净值、份额 |
| C-02 | **`Transaction.amount` 是现金流唯一口径** | `amount` 始终代表"实际资金进出额"，是 XIRR 与份额申赎的唯一输入 |

| C-06 | **空状态必备** | 每个新页面/新卡片都必须有"无组合 / 无数据 / 加载中 / 请求失败"四态，不得白屏或报错 |
| C-07 | **复用优先** | 优先复用 `components/ui/*`（shadcn）、`features/*` 已有组件，禁止重复造轮子 |

## 3. 模块一：概览（Dashboard）

### 3.1 目标

- 一屏呈现核心收益指标与趋势，作为用户的默认落地页
- 提供统一的时间维度切换（年/月/周/日），驱动页面内所有图表联动
- 作为流量枢纽，向持仓 / 交易 / 分析页下钻

> ⚠️ **口径提醒（源自 D-01 / C-08）**：概览页上的**全部指标均来自收益计算引擎**，即 `AssetSnapshot` + `Transaction` + `daily_nav` + `daily_xirr`。
> **「当前总资产」取自最新一条 `AssetSnapshot.totalAsset`，不是持仓模块的「Σ 标的市值 + 现金余额」。**
> 二者在用户未点「一键同步」时可能不相等，这是**预期行为，不是 bug**。概览页**不得**读取任何持仓表。

### 3.2 核心用户故事

## 4. 模块二：持仓（Holdings）

### 4.1 ⚠️ 前置说明：这是本次最大的架构缺口

当前系统是**纯组合级现金流模型**：`Transaction` 只有 `date / type(BUY|SELL) / amount / note`，`AssetSnapshot` 只有 `totalAsset`。系统**完全不知道用户持有什么标的**。因此"持仓"不是打磨，而是**从零建模**。

我评估了三种方案：

| 方案                     | 做法                                                                                         | 对现有金融口径的影响                                                             | 工作量 | 评价                                    |
| ---------------------- | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------- | --- | ------------------------------------- |
| **A. 持仓快照法**（✅ **推荐**） | 新增 `Security`（标的）与 `Holding`（标的×日期的持仓快照，手工录入数量/成本/现价）。组合总市值 = Σ 标的市值，可一键回填 `AssetSnapshot` | **零影响**。XIRR/净值仍走组合级现金流 + 快照，`nav.service.ts` / `xirr.service.ts` 一行不改 | 中   | 风险最低，能立刻交付用户价值，且字段为方案 B 预留            |
| B. 交易明细法               | 改造 `Transaction` 为标的级（symbol + quantity + price + fee），持仓由流水推导                             | 需重构交易与重算链路，存量数据迁移复杂，且仍解决不了"现价从哪来"                                      | 高   | 本次不做，作为 P2 演进方向                       |
| C. 仅组合概览               | 不引入标的，只展示各组合市值占比                                                                           | 零影响                                                                    | 低   | 与 概览页的组合对比重复，**不满足用户"持仓明细"诉求** |

**结论**：本次采用**方案 A**，并在字段设计上向方案 B 兼容（`Holding` 与 `Transaction` 共用 `securityId` 外键）。

> **注意**：自动获取行情估值已在基础 PRD v1.2 中从 Out of Scope 移除，列为 In Scope。具体实现方式（数据源、更新频率、缓存策略）待架构设计。在行情自动获取功能落地前，现价由用户手工录入或导入。

### 4.2 目标

- 让用户看清"钱具体分布在哪些标的上"，补齐当前只有总额的盲区
- 与资产快照双向校验联动，提升数据准确性
- 全程不触碰已验证的 XIRR / 净值计算逻辑

### 4.5 成本口径定义（P0 必须明确）

**默认采用「移动加权平均成本」**：

```
新买入后 avgCost = (原数量 × 原 avgCost + 本次买入金额含费用) / (原数量 + 本次数量)
卖出时   avgCost 不变，仅减少 quantity（卖出盈亏单独计入已实现盈亏）
```

**选择理由**：与国内券商 App / 基金 App 展示口径一致，用户零学习成本；FIFO 需逐笔批次跟踪，复杂度高且个人投资者少用，列入 P2。

> ⚠️ 方案 A 下 `avgCost` 由**用户手工录入**（可直接抄券商 App 的持仓成本），系统不自动推算。自动推算需方案 B 的标的级交易流水支撑。此点已列入待确认问题 Q-04。

```prisma
model Security {
  id          String       @id @default(uuid())
  portfolioId String       @map("portfolio_id")
  code        String       // 标的代码，如 600519
  name        String       // 标的名称
  type        SecurityType @default(STOCK)
  currency    String       @default("CNY")
  createdAt   DateTime     @default(now()) @map("created_at")
  updatedAt   DateTime     @updatedAt @map("updated_at")

  portfolio Portfolio @relation(fields: [portfolioId], references: [id], onDelete: Cascade)
  holdings  Holding[]

  @@unique([portfolioId, code])
  @@index([portfolioId])
  @@map("securities")
}

enum SecurityType { STOCK FUND BOND CASH OTHER }

model Holding {
  id          String   @id @default(uuid())
  portfolioId String   @map("portfolio_id")
  securityId  String   @map("security_id")
  date        DateTime @db.Date
  quantity    Decimal  @db.Decimal(18, 6)              // 持仓数量
  avgCost     Decimal  @map("avg_cost")     @db.Decimal(18, 6)  // 移动加权平均成本价
  marketPrice Decimal  @map("market_price") @db.Decimal(18, 6)  // 现价（手工录入）
  note        String?
  createdAt   DateTime @default(now()) @map("created_at")
  updatedAt   DateTime @updatedAt @map("updated_at")

  portfolio Portfolio @relation(fields: [portfolioId], references: [id], onDelete: Cascade)
  security  Security  @relation(fields: [securityId], references: [id], onDelete: Cascade)

  @@unique([securityId, date])
  @@index([portfolioId, date])
  @@map("holdings")
}
```

| `GET /api/portfolios/:id/holdings/dates` | 有持仓数据的日期列表（供日期选择器） |
| `POST /api/portfolios/:id/holdings/sync-snapshot` | 以持仓市值合计 upsert 当日资产快照并触发重算 |

**关联现有模块**：`sync-snapshot` 复用 `snapshot.service.ts` 的 upsert + `recalculation.service.ts` 的重算链路，不新写计算逻辑。

### 4.8 一键同步：持仓合计 → 当日资产快照（D-05 落位章节）

**目标**：让用户无需手动抄写，就能把「持仓模块算出的组合总市值」一键写入 `AssetSnapshot.totalAsset`，从而让 概览页的「当前总资产」与该数字一致。

**四场景定义（架构师勿自行推测）**：

**场景一 · 覆盖策略（Coverage Strategy）**
- `POST /api/portfolios/:id/holdings/sync-snapshot` 调用 `snapshot.service.ts` 的 `upsert`，以 `(portfolioId, date)` 为唯一键。
- 若当日快照**不存在**：创建 `AssetSnapshot { totalAsset: 持仓合计, note: '由持仓模块同步' }`。
- 若当日快照**已存在**：`update` 仅覆盖 `totalAsset` 字段，其余字段（如 `note`、历史数据）**原样保留**，不丢失。
- **严禁**触发任何 `Holding` / `DividendRecord` / `FeeRecord` 的写操作（见 C-09）。

**场景二 · 日期对应（Date Mapping）**
- `date` 取**当前所选持仓日期**（HOLD-P0-04 日期选择器的值），必须与持仓 `Holding.date` 同源，不得自造日期。
- 若所选日期晚于最新 `AssetSnapshot` 日期，则新快照排在其后，不影响历史序列。
- 与边界 2 一致：这是「两个独立数字」中的**资产快照侧**数字，与持仓展示的「Σ 标的市值 + 现金余额」在用户未同步前可不等。

**场景三 · 重算范围（Recalculation Scope）— 🔴 修复存量缺陷**
- 调用 `recalculation.service.ts` 的 `recalculateFromDate(date)`，按日期升序对该日及之后**全部日期**重算净值与 XIRR。
- ⚠️ **必须修复 §8.2 披露的缺陷**：现有 `snapshot.upsert()` 覆盖历史快照时**只重算当日、未做级联重算**。本接口必须改为级联触发——覆盖当日快照的同时，把后续所有日期的净值 / XIRR 一并重算，避免「当日数字变了但历史序列没动」的脏数据。
- 这点直接呼应边界 1：**触发计算的源头是资产快照被改写，不是持仓表被改写**。

**场景四 · 反馈形式（Feedback Form）**
- 调用后前端 toast 明确：「已同步 ¥X 至资产快照（日期 YYYY-MM-DD），并触发该日及之后 N 天重算」。
- 与 TXN-P0-04 的「重算结果反馈」口径一致（复用 `recalculation.service` 返回的 `{ fromDate, affectedDays }`）。
- 失败时报错明确指向具体原因（快照写入失败 / 重算失败回滚）。

### 7.4 UserPreference 字段定义（SET-P0-02）

| 字段 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `defaultPortfolioId` | String? | null | 登录后自动选中的组合 |
| `defaultGranularity` | Enum(`day/week/month/year`) | `month` | 概览页与分析页默认时间维度 |
| `defaultDateRange` | Enum(`3m/1y/ytd/all`) | `1y` | 默认日期范围快捷项 |
| `aggregation` | Enum(`last/avg`) | `last` | 周期聚合方式（从 localStorage 迁移） |
| `weekStartsOn` | Int (0=周日, 1=周一) | `1` | 按周聚合的周起始日 |
| `navDecimals` | Int | `4` | 净值展示小数位 |
| `xirrDecimals` | Int | `2` | XIRR 百分比小数位 |
| `theme` | Enum(`light/dark/system`) | `system` | 主题（P1） |
| `staleDays` | Int | `3` | 快照过期提醒阈值（P1） |

```prisma
model UserPreference {
  id                 String   @id @default(uuid())
  userId             String   @unique @map("user_id")
  defaultPortfolioId String?  @map("default_portfolio_id")
  defaultGranularity String   @default("month") @map("default_granularity")
  defaultDateRange   String   @default("1y")    @map("default_date_range")
  aggregation        String   @default("last")
  weekStartsOn       Int      @default(1)       @map("week_starts_on")
  navDecimals        Int      @default(4)       @map("nav_decimals")
  xirrDecimals       Int      @default(2)       @map("xirr_decimals")
  theme              String   @default("system")
  staleDays          Int      @default(3)       @map("stale_days")
  createdAt          DateTime @default(now())   @map("created_at")
  updatedAt          DateTime @updatedAt        @map("updated_at")

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@map("user_preferences")
}
```

> 采用**列式存储**而非 JSON：便于后端校验、Prisma 类型安全、可加索引。字段数量可控（< 15）。

### 8.2 ✅ 最高风险点已消除

**`TransactionType` 维持 `BUY` / `SELL` 两值不变（C-10）。**

`xirr.service.ts` 与 `nav.service.ts` **无需任何改造**——现有按 `type === 'BUY'` / `type === 'SELL'` 二分判断保持不变。这是 v1.1 决策中确认的核心风险消除方案。

**分红与费用的记录方式**：

| 数据类型 | 记录位置 | 是否参与 XIRR | 是否参与净值计算 |
|---------|---------|-------------|---------------|
| `BUY`（存入） | `Transaction` | ✅ 负现金流 | ✅ 申购（增加份额） |
| `SELL`（取出） | `Transaction` | ✅ 正现金流 | ✅ 赎回（减少份额） |
| 现金分红 | `DividendRecord`（持仓模块） | ❌ 不参与 | ❌ 不参与 |
| 手续费/费用 | `FeeRecord`（持仓模块） | ❌ 不参与 | ❌ 不参与 |

> **设计理由**：将分红/费用从 `Transaction` 剥离到持仓模块独立建表，从根本上避免了 `xirr.service.ts` / `nav.service.ts` 的改造风险。用户可在持仓模块按标的查看累计分红与累计费用，不影响收益计算引擎。

**必须补充的单元测试**：
- 存量纯 `BUY`/`SELL` 数据的回归测试（结果必须与本次改动前完全一致）
- `DividendRecord` / `FeeRecord` 的 CRUD 与权限隔离（`userId` 过滤）
- 分红/费用数据不污染 `daily_nav` / `daily_xirr` 的集成验证
