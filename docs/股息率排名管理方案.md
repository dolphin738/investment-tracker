## 1. 背景与目标

### 1.1 为什么采用「调整后 TTM/LFY 含预案」口径

股息率（Dividend Yield）是把「公司现金分红」与「市价」配比形成的派生指标。纯 TTM 与纯 LFY
各有缺陷：

- **TTM 失真**：分红频率变化（如从每年一次变为每年两次）时，过去若干报告期分红对应的盈利区间
  可能超过一年，股息率被高估。

- **LFY 滞后**：只统计最近完整财年，会忽略最新一期已公告分红。

本方案采用**调整后的 TTM 含预案口径**：先判断「最新分红对应的分红盈利区间是否等于 1 年」，
等同时取 TTM，否则退回 LFY，从而在「失真」与「滞后」之间取平衡。

### 1.2 功能目标

在已定稿的股息率口径之上，构建完整的数据链路与前端呈现：

1. **数据采集**：常规分红通过金融数据接口页「股息列表」分类已配置的「东财-分红配送」接口
   按报告期获取股票名称/代码与分红信息（同时负责证券主数据的新增与更新）；**无报告期归属的
   特别分红**通过「公司公告」分类的「沪深京 A 股公告」接口每日扫描检测（`symbol=财务报告`
   预过滤 + 标题正则二筛），命中后由「股息列表」分类的「新浪-分红配股」接口逐只补充（§6.8）；
   通过「证券行情」分类已配置的「腾讯财经-A股\_场内基金\_港股\_行情」接口获取最新股价
   （收盘后作为当日收盘价）。
2. **数据源可切换**：股息源在「股息列表」分类接口中选、行情源在「证券行情」分类接口中选，
   均可在设置页切换（接口本身在金融数据接口页维护）。
3. **自动任务**：每季度最后一天自动抓取股息数据；每日 06:00（含周末/节假日）扫描公告、
   补充特别分红（§6.8）；每日收盘后抓取收盘价。
4. **留存**：股息数据保存 5 年（支撑连续分红统计与审计）。
5. **排名管理页**：**有分红记录公司**的股息率排名，各列可排序（默认股息率降序）。
6. **波动曲线**：单只股票过去一年股息率波动曲线。
7. **阈值标色**：股息率高于绿色阈值显示为绿色、低于红色阈值显示为红色，两个阈值可配置。
8. **反推价格**：给定目标股息率，计算股票「应为」的价格。
9. **专门展示页**：股息率前 20 + 连续分红公司榜，剔除近两年无分红公司。
10. **设置集中化**：阈值与数据源选择统一放入设置页-偏好设置的独立「股息率」TAB（§10.4）。

**可衡量验收标准**：

| # | 验收项 | 目标值 |
| --- | --- | --- |
| 1 | 日线抓取成功率 | ≥ 99%（单日全量 ≤ 10s） |
| 2 | 冷启动（20 报告期回补） | ≤ 3 分钟（含限速等待，见 §6.1） |
| 3 | 股息率与手工核算样例偏差 | 0（以 §2.6 四时点为基准） |
| 4 | 曲线末点与列表快照值 | 完全一致（§9 契约） |
| 5 | 覆盖证券数 | = `security_dividends` 内去重证券数（§1.3） |

### 1.3 适用范围与边界

- **纳入**：沪深京 A 股（`securities` 主数据 `asset_class=STOCK`、交易所 `SH/SZ/BJ`）。
- **排除 B 股**：必须显式排除 `code LIKE '900%'`（沪市 B 股）与 `code LIKE '200%'`（深市 B 股）。
  > **依据（易踩坑）**：`classification.classify_astock()` 会把 900xxx/200xxx 判为「B股」，
  > 而 `_ASSET_CLASS_TO_ENUM` 又将「B股」映射为 `SecurityType.STOCK`（`services/classification.py`
  > L275-279、L486-501）。因此仅靠 `asset_class=STOCK AND exchange IN (SH,SZ,BJ)` **会误纳全部 B 股**
  > ——B 股以美元/港币计价，价格与分红币种均与 A 股不同，混入将污染排名。**必须按代码前缀排除**。
- **排除**：场外/老三板（按 `is_dropped` 标记）。
- **退市 / 代码变更（决策 A14）**：**不做代码归并，历史归属原代码**——证券从 `securities`
  消失（退市）后其历史分红与价格**保留不清理**（审计可追溯），但排名按 `securities`
  存在性自然剔除；代码变更会新建 `master_id`，连续分红年数因此断裂属**预期行为**，
  不跨代码合并。
- **覆盖度语义（重要）**：本方案的「全量排名」指**已进入 `security_dividends` 的有分红记录公司之间**
  的排名，**不等于**全市场 5873 只 A 股。代码清单由分红事件表反查得到（§6.2），
  不依赖全市场主数据同步。管理页应展示「当前覆盖 N 家有分红记录的公司」，避免用户误解为全市场。

**Non-goals（本次不做）**：港股/基金/债券/指数；用户持仓分红记录（`DividendRecord`，属持仓域）；
交易信号、选股推荐、数据导出、移动端适配；多用户权限细分（全局配置为单份，见 §5.4）。

## 2. 口径算法（单一事实来源）

### 2.1 输入模型

**报告期按季度粒度**：半年报 = 第 2 季度报告期（Q2），年报 = 第 4 季度报告期（Q4），
另有一季报（Q1）/三季报（Q3）。一年共 **4 个季度报告期**，正好构成一个财年。

单条分红记录 `r` 必带字段（详见 §5.1）：

| 字段 | 说明 |
| --- | --- |
| `master_id` | 证券主数据（`securities`） |
| `report_year` | 报告期所属财年（如 2026） |
| `report_quarter` | 季度报告期（1~4；半年报=2、年报=4、一季报=1、三季报=3） |
| `cash_per_share` | 每股现金分红（元；源为「每 10 股派 X 元」时除以 10 折算） |
| `status` | 分红事件生命周期状态（见 §3.1） |
| `ex_dividend_date` | 除权除息日（用于曲线归位与留存判定，见 §3.4） |

按 `(report_year, report_quarter)` 倒序排列得到序列 `D`（`D[0]` 为最新分红 `L`）。
「上一财年同期」定义：`(report_year - 1, 相同 report_quarter)`。

**特别分红（SPECIAL）的落格规则（决策 A6）**：特别分红没有真实报告期，落格锚点取
**公告日期**——`report_year` = 公告年，`report_quarter` = 公告月份的日历季度（`ceil(月/3)`）。
TTM/LFY 的分子是财年 4 格求和，季度取值只影响年内曲线形状、不影响年度分子；
财年归属由公告年唯一确定（除权日可跨年漂移，公告日一经发布不变，见 §3.4）。
常规分红**不适用**本规则——直接使用东财返回的报告期（§6.1）。

### 2.2 口径选择（TTM / LFY）

设最新分红 `L = D[0]`，判定规则：

| 条件 | 口径 | 判断依据 |
| --- | --- | --- |
| `L.report_quarter == 4`（年报） | **TTM** | 分红盈利区间 = 1 年 |
| `L` 非 Q4，且上一财年同期（`year-1, 相同 quarter`）存在分红 | **TTM** | 盈利区间 = 1 年 |
| `L` 非 Q4，且上一财年同期无分红 | **LFY** | 锚定最近完整财年，避免跨财年混算 |

### 2.3 分子（每股，元）

- **TTM（真 4 期，含预案）**：从最新分红 `L` 所在季度格子向前取满 **4 个季度格子**
  （跨年末尾衔接，形成滚动 12 个月窗口），每个格子取该季度报告期的分红（无分红格子记 0），求和。
  **按季度格子数计数，而非按分红事件条数**。

- **LFY**：`分子 = 最近一个完整财年（该年 Q1–Q4）全部分红之和`。

- **税前口径**：分子采用**税前**每股现金分红（东财「现金分红-现金分红比例」为每 10 股税前派息）。
  A 股股息红利税按持股期限差异化（>1 年免征、1 月~1 年 10%、<1 月 20%），**到手金额因人而异**，
  无法统一，故采用行业通用的税前股息率。**前端列头与卡片必须标注「税前」**。

### 2.4 股息率

```
股息率（比率，小数形式） = 分子 / 最新每股价格 P
```

`P` 取**不复权收盘价**（元/股），与每股现金分红单位一致；价格缺失则整体返回缺失（§3.3）。

> **单位契约（全局强制，勿改）**
> - **存储与 API 传输一律用小数比率**（0.05 表示 5%）；
> - **仅用户输入项（阈值、target ratio）与展示层用百分数**；
> - 前端统一复用 `lib/utils.ts` 的 `formatPercent`（实现为 `(num*100).toFixed(d)+'%'`，
>   输入小数 0.05 → 输出 `5.00%`）。
>
> **依据**：`web/src/lib/utils.ts` 的 `formatPercent` 注释与实现确认为"输入小数形式（0.1234）→ 12.34%"，
> 且 XIRR 等既有比率字段一律小数存储。若改按百分数存储，则 `formatPercent(5.00)` 会显示 `500.00%`。
> 本条是此前版本单位互斥（存储小数、阈值存 5.00）的修正结论。

### 2.5 判定伪代码

```python
def _cells(D, y, q):
    # 从 (y,q) 向前取满 4 个季度格子，跨年末尾衔接
    cells = []
    for i in range(4):
        cells.append(sum(r.cash_per_share for r in D
                        if r.report_year == y and r.report_quarter == q and r.status != REJECTED))
        q -= 1
        if q == 0: q, y = 4, y - 1
    return sum(cells)

def dividend_yield(D, price):
    """纯函数：无 IO，入参为分红序列 + 现价，输出 (mode, numerator, yield, ref_ids)。

    曲线逐点计算与快照计算**必须复用本函数**（§9 契约），保证曲线末点 == 快照值。
    """
    D = sorted_desc(D)                 # (year, quarter) 倒序
    L = D[0]
    same_quarter_last_year = any(r for r in D if r.report_year == L.report_year - 1
                                 and r.report_quarter == L.report_quarter
                                 and r.status != REJECTED)
    if L.report_quarter == 4 or same_quarter_last_year:
        mode, numerator = TTM, _cells(D, L.report_year, L.report_quarter)
    else:
        mode, numerator = LFY, _cells(D, L.report_year - 1, 1)   # 最近完整财年(上年 Q1–Q4)
    if price is None or numerator is None:
        return mode, numerator, None, []
    return mode, numerator, numerator / price, [r.id for r in ref_records]
```

### 2.6 示例对照与口径后果

报告期为季度粒度（半年报=Q2、年报=Q4），**近 4 个报告期 = 最近一个财年的 4 个季度报告期**，
不会把 2026 与 2025 两个财年混算（否则会把两年利润一起当分子、股息率高估一倍）。

**示例 A**（股息频次从年报增至中报+年报）
`D = [2026半年报(Q2)1.3, 2025年报(Q4)6.1, 2025半年报(Q2)2.4, 2024年报(Q4)5]`

- 半年报时：`L=2026Q2`，上一财年同期（2025 Q2）**有**分红 → **TTM**。
  4 格 = `[2026Q2=1.3, 2026Q1=0, 2025Q4=6.1, 2025Q3=0]` → `分子 = 1.3 + 6.1 = 7.4`。

- 年报时：`L=2026Q4`（年报预案 5）→ **TTM**。
  4 格 = `[2026Q4=5, 2026Q3=0, 2026Q2=1.3, 2026Q1=0]` → `分子 = 5 + 1.3 = 6.3`。

**示例 B**（年报单一，中报首次出现）
`D = [2026年报(Q4)3（预案）, 2026半年报(Q2)2.4, 2025年报(Q4)5.3]`

- 半年报时：`L=2026Q2`，上一财年同期（2025 Q2）**无**分红 → **LFY**。
  `分子 = 最近完整财年(2025)全部 = 5.3`。

- 年报时：`L=2026Q4`（年报预案 3）→ **TTM**。
  4 格 = `[2026Q4=3, 2026Q3=0, 2026Q2=2.4, 2026Q1=0]` → `分子 = 3 + 2.4 = 5.4`。

（此前误把「4 期」当「4 条分红事件」写成 14.8/10.7，是把 2026 与 2025 两个财年混算、高估；
此处按**4 个季度报告期 = 一个财年**修正。这四个时点是纯函数单测的**黄金断言基准**。）

## 3. 分红事件生命周期与失效机制

### 3.1 状态机

```
PROPOSED（预案已公告）
   │ 派息划转落地            │ 预案否决/撤回       │ 金额修订
   ▼                         ▼                    ▼
  PAID                    REJECTED             PROPOSED(新金额)
```

- 仅 `PROPOSED` 与 `PAID` 计入分子（含预案口径），`REJECTED` 一律剔除；

- `REJECTED` / `PAID` 金额变化（从 `PROPOSED` 迁移）为**失效事件**，触发该证券派生值即刻重算；

- 每条派生结果落库时附带 `mode` 与**参与计算的分红记录 id 清单**（`ref_div_ids`），
  可从结果反查来源（data-lineage/provenance，支持审计与定点重算）。

### 3.2 东财「方案进度」→ `status` 映射（实测校准，精确匹配）

> **强制：必须使用精确值匹配，禁止用「包含」匹配。**
> 若按"含『分配』→ PAID"匹配，`取消分配` 会被**误判为 PAID**，导致已取消的分红计入分子、
> 股息率虚高（方向性错误，比漏算更坏）。

| 东财「方案进度」取值 | `status` | 实测条数（16303 行样本） |
| --- | --- | --- |
| `实施分配` | `PAID` | 16277 |
| `预披露` | `PROPOSED` | 21 |
| `董事会决议通过` | `PROPOSED` | 1 |
| `取消分配` | `REJECTED` | 3 |
| `股东大会否决` | `REJECTED` | 1 |

未识别取值：**记日志跳过，不得臆测**（不静默归入任一状态）。新增取值须回补本表并补单测。
实测方法与样本见附录 A。

### 3.3 事件驱动失效表

| 失效/重算事件 | 触发源 | 动作 |
| --- | --- | --- |
| 新分红预案公告 | 股息抓取 | 写入 `PROPOSED` 记录 → 重算 |
| 派息划转落地 | 股息抓取（状态→PAID） | 状态迁移 → 重算 |
| 预案否决/撤回 | 股息抓取（状态→REJECTED） | 剔除记录 → 重算 |
| 预案金额修订 | 股息抓取 | 改金额 → 重算 |
| 收盘价刷新 | 日线抓取 | 重除股息率（分子不变时仅重除） |

- 无固定 TTL，**事件驱动**刷新；派生值**永远可从源数据重算**，快照不是唯一正确性来源
  （Iron Law：NO DERIVED VALUE WITHOUT RECOMPUTE）。

### 3.4 日期字段语义（重要，三个日期不可混用）

A 股分红涉及三个不同日期，**含义与用途均不同**：

| 日期 | 含义 | 本方案是否采集 | 用途 |
| --- | --- | --- | --- |
| 预案公告日 | 董事会披露分红预案 | 否 | — |
| **股权登记日** | 确定享有分红资格的股东名册 | 可选（`record_date`） | 更精确的历史归位锚点 |
| **除权除息日** | 次一交易日，价格下调 | **是（`ex_dividend_date`）** | 曲线归位、留存判定 |

> **命名约束**：字段必须命名为 `ex_dividend_date`（除权除息日），**不得沿用 `pay_date`**。
> 东财 `stock_fhps_em` 返回列中**没有「派息日」**（只有 预案公告日/股权登记日/除权除息日），
> 原方案把该字段描述为"派息/除息日"属语义混用，会导致归位锚点用错。

**除权跳变提示**：`close` 为不复权价，除权除息日价格会下移，而分子在同日纳入该笔分红 →
曲线在该点出现向上跳变。前端应在曲线上标注除权事件标记（§10.2）。

### 3.5 降级与缺失语义

- 分红记录缺失或现价缺失 → 返回 `null`（**缺失而非 0**），避免伪造低股息率误导；

- 派生快照陈旧且源不可达 → 保留上次快照并标记 `stale=true`，前端标灰并提示，不静默展示。

### 3.6 特别分红（SPECIAL）生命周期（公告扫描驱动，决策 A6）

东财按报告期接口**不含**无报告期归属的特别分红（茅台 2022/2023 两笔实证，附录 A.6），
此类分红由每日公告扫描（§6.8）驱动生命周期，状态机与 §3.1 一致：

| 阶段 | 触发 | 动作 |
| --- | --- | --- |
| `PROPOSED` | 公告标题命中分红关键词（预案/方案类，如「中期利润分配方案公告」「特别分红」） | 新浪补充金额 → 写 SPECIAL 行（公告日期锚点落格，§2.1），`ex_dividend_date` 为 NULL |
| `PAID` | 实施类公告命中（如「权益分派实施公告」）且新浪该证券存在进度=实施的对应行 | 按「同证券 + 金额相等」匹配存量 PROPOSED → 置 PAID 并回填 `ex_dividend_date`；无匹配则新建 PAID 行 |
| `REJECTED` | 公告标题含 `取消\|终止` + 分红关键词 | 对应 SPECIAL 行置 REJECTED |

- **不做超时自动否决**（会误杀延期实施）；超 2 个报告期未实施的 PROPOSED 置 `stale` 标记 + 站内信。
- **去重（防双计，双向）**：见 §6.8——SPECIAL 行与东财报告期行可能描述同一笔分红
  （如茅台 2024 中期分红东财挂 2024Q3 报告期），必须按「`ex_dividend_date` 相等」或
  「`(report_year, report_quarter, cash_per_share)` 全等」互斥。
- 曲线"可见"锚点：SPECIAL 行 `ex_dividend_date` 为 NULL 时用 `announcement_date`
  （即 `COALESCE(ex_dividend_date, announcement_date)`，§9）。
- SPECIAL 行的写入/迁移同样走 §3.3 事件驱动重算。

## 5. 数据模型

五张表：分红事件表、市场日线表、派生快照表、全局配置表、交易日历表。

### 5.1 分红事件表 `security_dividends`（新增）

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `master_id` | FK→`securities` 主数据（**非** `portfolio_securities`，见 §4 命名约束） |
| `report_year` | 报告期所属财年（如 2026） |
| `report_quarter` | 季度报告期（1~4；半年报=2、年报=4、一季报=1、三季报=3） |
| `period_type` | 报告期类型（`ANNUAL` / `INTERIM` / `QUARTERLY` / `SPECIAL`） |
| `cash_per_share` | 每股现金分红（元；源为「每 10 股派 X 元」时除以 10 折算） |
| `status` | `PROPOSED` / `PAID` / `REJECTED`（映射见 §3.2） |
| `ex_dividend_date` | 除权除息日（**非派息日**，见 §3.4） |
| `announcement_date` | 公告日期（**SPECIAL 行的财年/季度落格锚点**，§2.1；东财报告期行可空） |
| `record_date` | 股权登记日（可选，东财有该列，作为更精确的归位锚点备用） |
| `source` | 来源接口名 + 东财原始股息率（**不采信其股息率，仅作附注**） |
| `created_at` / `updated_at` | 创建 / 更新时间 |

**唯一约束** `(master_id, report_year, report_quarter, period_type)`，幂等 upsert。

> **实测依据（决策 A3/A7）**：对 `stock_fhps_em` 抓取 8 个报告期（2021Q4~2025Q2，
> 含 4 个年报 + 4 个半年报，合计 16303 行），**同一报告期内同一「代码」从未出现多行**
> （`dup_codes=0`）——东财单源下唯一键不会覆盖丢行。**但**唯一键仍须扩展 `period_type`：
> 决策 A6 引入的 SPECIAL 补充行与东财报告期行会落在同一 `(master, year, quarter)` 格
> （实证：茅台 2022 特别分红与 2022 年报分红同落 2022Q4，若不加 `period_type` 则后写覆盖先写、
> 分子少算一笔，见附录 A.6）。同格允许报告期行与 SPECIAL 行并存，
> 由 §6.8 双向去重保证不双计。

`period_type` 推导规则：**东财报告期行**按 `report_quarter` 推导
（`==4 → ANNUAL`、`==2 → INTERIM`、`∈{1,3} → QUARTERLY`）；
**新浪补充行**一律为 `SPECIAL`（由采集路径决定，不依赖东财「方案」列文本判定，§6.8）。

### 5.2 市场级日线收盘价表 `market_security_daily_prices`（新增）

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `master_id` | FK→`securities` 主数据 |
| `trade_date` | 交易日（Date） |
| `close` | 收盘价（Numeric(18,6)，**不复权**） |
| `source` | 来源接口名 |
| `fetched_at` / `created_at` | 抓取/创建时间 |

唯一约束 `(master_id, trade_date)`（幂等 upsert，同日重抓覆盖 close）。
该唯一约束同时服务曲线的 `WHERE master_id=? ORDER BY trade_date`。

**容量估算**：覆盖有分红记录公司约 2500~3500 只（§1.3），按 243 交易日/年、保留 2 年
≈ **120~170 万行**，含索引约 0.3~0.6 GB。快照表仅数千行，**无需物化视图或缓存**。

### 5.3 派生快照表 `security_dividend_yields`（新增）

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `master_id` | FK→`securities` 主数据，**唯一**（每证券一行，仅存最新派生值） |
| `mode` | 口径（`TTM` / `LFY`，判定见 §2.2） |
| `numerator_per_share` | 分子（每股，元，Numeric(18,6)） |
| `dividend_yield` | 股息率（**小数比率**，Numeric(18,6)；0.05 = 5%），分母缺失为 `null` |
| `latest_price` | 计算所用最新收盘价（与日线表快照一致） |
| `latest_trade_date` | 该 `latest_price` 对应交易日（供前端展示「数据截至」） |
| `consecutive_years` | **连续分红年数**（SmallInt，定义见 §8.2，≤5） |
| `last_dividend_year` | **最近一次有分红的财年**（Integer，供"近两年无分红"判定，见 §8.2） |
| `ref_div_ids` | 参与计算的 `security_dividends.id` 清单（JSONB，审计/定点重算） |
| `stale` | 陈旧标记（定义见 §7） |
| `suspicious` | 异常股息率标记（**决策 A12**：`yield ≤ 0` 或 `yield > 0.30` 置 true，不入 Top20，管理页标警示） |
| `computed_at` | 本次重算时间戳 |

每证券一行、仅存最新快照；`mode/numerator_per_share/latest_price/dividend_yield/consecutive_years`
任一源变化即整行重建（变更集重算，见 §7）。

**建议索引**（配合 §8 排名查询）：

- `ix_dividend_yields_rank (dividend_yield DESC NULLS LAST, master_id)` —— 排名主查询
- `ix_dividend_yields_consecutive (consecutive_years DESC)` —— 连续分红榜

> `consecutive_years` 与 `last_dividend_year` 必须为落库列：排名页要按连续年数排序与过滤、
> Top20 要按"近两年无分红"剔除，若查询时现算则无法在 SQL 层过滤排序
> （`paged()` 是裸 `limit/offset`，无内存二次过滤）。

### 5.4 全局配置表 `dividend_yield_settings`（新增，单行）

| 字段 | 说明 |
| --- | --- |
| `id` | 主键（单行，迁移时 seed 默认行） |
| `green_threshold` | 绿色阈值（**小数比率**，Numeric(5,4)，默认 `0.05` = 5%） |
| `red_threshold` | 红色阈值（**小数比率**，Numeric(5,4)，默认 `0.03` = 3%） |
| `dividend_report_source_interface_id` | **主源**：FK→`quote_provider_interfaces.id`，**`ondelete="SET NULL"`**；必须属分类 3 且为**按报告期全量**形态（当前「东财-分红配送」），供 §6.1 季度抓取 |
| `dividend_detail_source_interface_id` | **补充源**：FK→`quote_provider_interfaces.id`，**`ondelete="SET NULL"`**；必须属分类 3 且为**按证券逐只**形态（当前「新浪-分红配股」），供 §6.8 特别分红补充 |
| `price_source_interface_id` | FK→`quote_provider_interfaces.id`，**`ondelete="SET NULL"`** |
| `updated_at` / `updated_by` | 更新时间 / 操作人 |

> **为什么不用 `user_preferences`**：数据源决定后台采集任务从哪个接口抓数，是**系统级**配置，
> 原设计存进 per-user 表、再靠"读首个 admin 的偏好"充当全局值，会引发三个问题：
> ① 非 admin 用户设置页也有该控件，改了不生效却像生效（幻影控件）；
> ② 若任务改为读当前用户偏好或 admin 判定出错，普通用户即可篡改全局采集来源；
> ③ "首个 admin"判定规则（按 `created_at` 还是 `id`、软删后怎么办）未定义且难以正确定义。
> 独立全局表使"首个 admin"概念彻底消失，配置只有一份，语义清晰。
>
> 已核实项目内**无现成全局配置表**（仅有 `job_configs` 系统任务表，以及
> `user_preferences`、`user_quote_sync_configs` 两张 per-user 表），故需新建本表。
> 阈值随之一并置于此（统一为全局标色标准，避免"一半 per-user、一半全局"的分裂）。

**校验规则**：

- 阈值为小数比率，范围 `0 < red_threshold < green_threshold ≤ 1`；非法返回 400（fail closed 不落库）；
- 接口 id **四重校验**：存在性 + 分类归属 + enabled + **调用形态**（主源必须在分类 3 且为按报告期全量
  形态、补充源必须在分类 3 且为按证券逐只形态、行情源必须在分类 2 且启用）；
  形态不符须拒绝——否则把逐只接口当主源会让 §6.1 的按报告期抓取直接失效。
- 仅在 `PUT` 侧校验，读侧兜底：接口失效时任务 fail fast 跳过并告警，**不静默换默认源**。

**默认值解析**：默认取对应分类内 `priority` 最小的 enabled 接口（复用
`_interfaces_for_category` 的排序语义，L321-335），由代码函数在 seed 与运行时解析，
**不用 DB `server_default` 表达**（无法表达该查询语义）。

## 6. 数据采集任务（复用既有调度器，注册为系统任务）

五条任务（第 4 条为手动触发的重建任务，第 5 条为每日公告扫描，§6.8）。

### 6.1 季度股息抓取 `dividend_quarterly_fetch`

- **触发**：每季度最后一天 02:00。cron 5 字段无法直接表达「季末」，采用
  `0 2 28-31 3,6,9,12 *` + **任务内 guard**（用 `today_app_tz()` 判定，非当季最后一天直接跳过并记日志）。

  > **时区**：调度器必须显式 `AsyncIOScheduler(timezone=APP_TZ)`（把
  > `core/date_utils._APP_TZ` 提为可导入常量）。当前 `scheduler.py` L360 未传 timezone，
  > 容器默认 TZ=UTC 会导致 `5 15 * * 1-5` 实际在北京时间 23:05 执行、季末 guard 跨日错判。
  > **所有 cron 一律按 UTC+8 解释。**

- **数据源**：配置选定的「股息列表」分类接口（当前「东财-分红配送」，SDK 方式，
  `endpoint=stock_fhps_em`），复用 `market_data_sync._fetch_sdk_raw` 调用机制。
  **已知缺口**：东财按报告期数据**不含无报告期归属的特别分红**（茅台 2022/2023 两笔实证，
  附录 A.6）——由 §6.8 每日公告扫描 + 新浪补充兜底。
  接口行 `params.date` 是单报告期示例值，任务按报告期迭代覆写调用，单次返回该报告期
  **全市场**分红送配表（源内部分页 500 条/页，无需按证券逐个请求）。

- **报告期范围（增量策略）**：

  - 查库得出「已有存量的报告期集合」与「缺失的报告期集合」（以任一证券存在即算该报告期已抓过）；
  - **缺失的报告期逐个补抓**（首次运行时即近 5 年 20 个）；
  - **重刷最近 4 个报告期**（滚动 12 个月窗口）。

  > **为什么是 4 个而不是 1 个（重要）**：A 股分红从"董事会预案 → 股东大会通过 → 实施分配"
  > 跨度常达数月，且存在"停止实施/否决"。若只重刷最新一个报告期，则上年度报告期
  > （除权除息日在次年 5—7 月）的 `status` 会**永远停在 `PROPOSED`**——
  > 若该方案最终被否决，`REJECTED` 永远抓不到，**已取消的分红会一直留在分子里，股息率长期高估**；
  > 且 `ex_dividend_date` 在预案阶段为空，也永远不会补上。
  > 重刷 4 期与 TTM 的"4 个季度格子"窗口同宽，可完整覆盖跨季度状态迁移。

  - 稳态下每次任务 = 增量 1 个新报告期 + 重刷最近 4 个（共 5 次调用）+ §6.3 清理滚出 5 年窗口的记录。

- **字段映射**（东财列 → 本方案模型）：

  | 东财列 | 映射 |
  | --- | --- |
  | `代码` / `名称` | **复用既有证券主数据 upsert**（`market_data_sync.py` L1130-1181：按 `asset_class+code` 查重、命中更新名称、未命中插入，批量 flush）——不新写主数据写入逻辑 |
  | 接口入参 `date`（报告期） | `report_year` + `report_quarter`（0331→Q1、0630→Q2、0930→Q3、1231→Q4） |
  | `现金分红-现金分红比例`（每 10 股派 X 元） | ÷10 → `cash_per_share`；送转股份列**不采集**（非现金分红，不入分子） |
  | `方案进度` | `status` 映射，**精确匹配**（§3.2 五值表），未识别记日志跳过 |
  | `除权除息日` | `ex_dividend_date` |
  | `股权登记日` | `record_date`（可选） |
  | `现金分红-股息率`（东财口径） | **不采信**，仅落 `source` 附注；股息率一律按本文 §2 自算 |

  > **复用 `_upsert_masters` 的前提**：`_upsert_masters`（L1130-1181）经 `_prepare_master_rows`
  > 按接口行的 `resp_code_field` / `resp_name_field` 取列。东财返回**中文列名**，
  > 故必须将该接口行的 `resp_code_field` 设为 `代码`、`resp_name_field` 设为 `名称`；
  > 域名解析走专用映射器，不读这两个字段。改动后须回归既有价格同步路径（`resp_code_field`
  > 是接口级共享字段）。

- **写入**：幂等 upsert 到 `security_dividends`（唯一键 master+year+quarter+period_type）；
  状态迁移按 §3.1 状态机。
  **东向去重**：upsert 前若同 `master_id` 存在满足「`ex_dividend_date` 与本行相等」**或**
  「`(report_year, report_quarter, cash_per_share)` 与本行全等」的 SPECIAL 行 → 删除该 SPECIAL 行
  （报告期行归属更准，胜出；防 §6.8 预案窗口双计）。

- **防击穿**：按报告期顺序串行调用，报告期间加请求间隔（复用 `_RATE_LIMITER` 按接口限速，
  `market_data_sync.py` L117-147）；单报告期失败记 `JobRunLog` 日志并续下一报告期。
  **断点即数据本身**：缺失报告期集合由 `security_dividends` 查表推导，无需额外游标存储——
  `JobRunLog` 模型无游标/JSONB 字段（仅 status/message/error），**不为此加列**。

- **耗时估算（已修正）**：`_RATE_LIMITER` 是**客户端固定间隔节流**（`10/min` → 6s），
  20 个报告期串行仅限速等待就需 ≥ 19×6 = **114s**，加上实测抓取 35-50s，
  **冷启动实际约 2.5-3 分钟**（原文"~1 分钟"低估约 2 倍，只算了服务端耗时未算客户端等待）。
  稳态 5 次调用约 30-45s。

- **事务与并发**：**按报告期独立 commit**（与"断点即数据本身"自洽，避免 7.6 万行长事务）；
  接口行必须配置 `timeout`（建议 15s）；`_run_job` 需增加 per-job 运行锁
  （复用 `_running_user_syncs` 思路，键为 `job_id`），防止 cron 与手动 trigger 并发。

- **抓取完成后**：对本次有变更的证券触发重算（仅变更集，不全局重建）。

### 6.2 每日收盘价抓取 `market_daily_close_fetch`

- **触发**：每交易日 15:05（UTC+8，`5 15 * * 1-5`），避开 15:00 收盘撮合瞬间。

- **数据源**：配置选定的「证券行情」分类接口（当前「腾讯财经-A股\_场内基金\_港股\_行情」，
  文本接口 `q=`，`code_param=q`，`code_prefix=auto`）。该接口为**按 code 批量查询**。

- **代码清单来源**：从 `security_dividends` **去重 `master_id`** 取得（§1.3 覆盖度语义），
  **不依赖全市场主数据同步**。分批调用复用 `_fetch_https_raw` 与接口行 `rate_limit` 限速。

- **批大小**：实测上限 900（URL ~8.1KB）全部正常；905（URL 8166B）返回 **HTTP 200 但空数据**
  （静默截断，比 414 更危险）；≥910 返回 HTTP 414。任务取常量 **800/批** 留安全余量。
  按覆盖 2500~3500 只计算，每日约 4~5 次请求。
  **必须校验「返回条数 == 请求条数」**，缺数批次记日志重试，不静默丢价。
  该 900 上限是**腾讯该端点**特性，须落到接口行配置（新增 `max_codes_per_request`），
  并补契约测试（httpx mock，不依赖真实网络）——探针脚本已删，结论需回归测试守护。

- **节假日与停牌防污（关键）**：cron `1-5` **只排除周末、不排除法定节假日**，
  原文档"周末/节假日 cron 本就不触发"的判断是错的。节假日任务照常执行，
  腾讯返回的是**上一交易日收盘价**，若以当天为 `trade_date` 写入会产生非交易日脏数据行。

  **处理（决策 A9，双防线，缺一不可）**：
  - **防线一·交易日历校验（主）**：任务启动先查 `market_trade_calendar`（§5.5），
    `today_app_tz()` **不在交易日历内 → 整批跳过并记日志**（法定节假日、周末均被拦下）。
    这是根本解法，不依赖接口返回内容。
  - **防线二·返回日期比对（备）**：解析腾讯返回行中的**日期/时间字段**
    （接口行新增 `resp_date_field` 配置）并与 `today_app_tz()` 比对，
    **不一致则整批跳过并记告警**，不写入。
  > 注意："返回条数 == 请求条数"校验在此场景**完全通过**（所有代码都有返回），
  > 无法发现该问题，必须靠上述两道防线。
  >
  > 停牌同理：停牌股返回停牌前价格，被当作当日收盘价写入，`stale` 也发现不了
  > （因为每天都"更新"了）——停牌由防线二（返回日期字段为上一交易日）拦截。
  > 日历表为空时防线一自动失效，防线二仍生效并触发告警（§5.5 降级语义）。

- **写入**：以**当天**为 `trade_date` 幂等 upsert（同日重抓覆盖 close）。

- **完成后**：刷新对应证券的 `latest_price` / `dividend_yield`（分子不变时仅重除）。

- **历史回补（新增，解决永久空洞）**：腾讯接口无历史回补能力，原设计下**任何一次采集失败
  都会在该证券曲线上留下永久空洞**。故新增可选的历史日线源（akshare `stock_zh_a_hist`），
  用于：① 冷启动回填；② 失败日补抓（任务扫描近 N 日缺失 `trade_date` 后逐证券回补）。
  若日后启用 akshare 全市场快照类接口（`stock_zh_a_spot_em`）并选它，则走 SDK 全量单次调用
  （`_fetch_sdk_raw` codes 为空形态）——两种调用形态按所选接口行的接入方式自动分派。
  **回补限速与批量（决策 A15，实测附录 A.11）**：`stock_zh_a_hist` 走 `push2his.eastmoney.com`，
  **约 18 只突发即触发限流且冷却 >60s**，不可逐只 1/s 直连。采用 **burst≈10 只 + 冷却 60–120s
  + 指数退避重试（60/120/300s）**，3000 只外推 **5–8 小时**，属多小时、**可断点续跑**任务。
  须**持久化已回补进度（按证券）**，并**每批记进度日志**（"已回补 X/N，下一冷却至 HH:MM"），
  进度经 §6.7 系统任务执行日志**只读呈现**；**不新增设置项**（速率复用接口 `rate_limit`，
  批量/冷却/退避为服务常量，补单测守护）。

### 6.3 五年留存清理 `dividend_retention_cleanup`

- **触发**：每年 1 月 1 日 03:00（UTC+8，`0 3 1 1 *`）。

- **规则**：**按 `report_year` 判定**，删除 `report_year < 当前年 - 5` 的 `security_dividends` 记录。

  > 原规则按 `ex_dividend_date`（原 `pay_date`）判定 5 年，会导致 `PROPOSED`/`REJECTED` 记录
  > 因该字段为 NULL 而**永不满足删除条件、无限堆积**；且留存窗口存在"报告期"与"除权除息日"
  > 两套口径（相差近半年）。统一按 `report_year` 后，与"连续分红年数按财年计数"口径一致，
  > 边界可预测（删除边界 = 当前年 − 5）。

- `market_security_daily_prices` 同步按 `trade_date` 只保留 2 年（曲线只需 1 年，留 1 年余量）。

- **顺带刷新交易日历（决策 A9）**：调用 akshare `tool_trade_date_hist_sina()` 拉取
  **未来 2 年 + 当前年**的交易日 upsert 进 `market_trade_calendar`（§5.5）；
  失败仅记告警、**不阻断清理**（日线任务降级依赖"返回日期比对"）。

- **清理前**重算受影响证券派生快照，保证删除旧记录后口径窗口不缺失。

### 6.5 数据源选择机制（接口分类驱动）

不引入代码内注册表，**金融数据接口页的接口配置行就是唯一事实来源**：

- **股息主源** = 配置表 `dividend_report_source_interface_id` 指向「股息列表」分类（id=3）下
  **按报告期全量形态**的 enabled 接口（§6.1 季度抓取）；
- **股息补充源** = 配置表 `dividend_detail_source_interface_id` 指向「股息列表」分类（id=3）下
  **按证券逐只形态**的 enabled 接口（§6.8 特别分红补充）；
- **行情源** = 配置表 `price_source_interface_id` 指向「证券行情」分类（id=2）下的 enabled 接口。

> **为什么股息要拆两个配置项（决策 A10）**：A6 落地后分类 3 下存在**两种不同调用形态**的接口，
> 二者不可互换——把逐只接口当主源会让按报告期抓取失效，把报告期接口当补充源则无法满足
> §6.8 的逐证券补充。故必须在配置层显式区分主源/补充源，并在写入时校验调用形态（§5.4 四重校验）。

调用形态由接口行自身决定，任务侧统一适配四种形态（均复用 `market_data_sync` 既有机制）：

| 接口形态 | 判定依据 | 调用方式 |
| --- | --- | --- |
| SDK 按报告期全量 | 分类 3 + SDK 接入（endpoint=akshare 函数名） | 按报告期迭代覆写 `params.date`，全量行返回 |
| SDK 全市场快照 | 分类 2 + SDK 接入且无 code 入参语义 | 单次全量调用（codes 为空形态） |
| HTTP 按 code 批查 | 分类 2 + 文本/JSON 接口（`code_param`） | 代码清单分批调用，`rate_limit` 限速 |
| SDK 按证券逐只循环 | SDK 接入且函数按单证券查询（`stock_history_dividend_detail`） | 对命中证券清单逐只循环（`params.symbol` 覆写），串行 + `_RATE_LIMITER`；新浪实测无频控（附录 A.8） |

- 分红行解析走**专用映射器**（东财中文列名 → 本方案模型，§6.1），价格行解析复用
  既有 `resp_code_field/resp_price_field` 机制。

- 新增数据源 = 金融数据接口页在对应分类下新增接口行（无需改代码），设置页下拉自动出现。

- 选定接口被停用/删除的兜底：任务读取配置时发现接口不存在或未启用 → **fail fast 记告警日志
  并跳过本次执行**（不静默换默认源，避免数据来源漂移无感知）。

> **与既有 priority 降级链的关系（需显式论证的偏离）**：既有行情同步是分类内按 `priority`
> 依次 fallback（`fallback_fetch`，`market_data_sync.py` L337-362）。本方案改用"单一选定源 +
> fail fast"，理由是**需要可审计的确定来源，不接受自动漂移**。但新任务仍必须调用
> `_fetch_sdk_raw`/`_fetch_https_raw`/`_call_interface_raw`，以继承 `_guarded_fetch`
> （限速 + 退避重试）与 `_mark_failure` 告警链路（`consecutive_failures ≥ 3` 发站内信）。

### 6.6 配置安全决策（configuration-and-automation-safety）

| 项 | 决策 |
| --- | --- |
| 变更类别 | **standard**（影响后台采集任务的数据来源，非低风险本地配置） |
| 变更路径 | 接口维护：金融数据接口页；阈值/源选择：设置页 TAB → `PUT /api/dividend-yield/settings`（唯一写入口，无旁路） |
| 契约 | 配置表单行；合法值 = 对应分类下 enabled 接口；阈值 `0 < red < green ≤ 1`；非法值 fail closed 400，不落库 |
| 验证 | 存在性 + 分类归属 + enabled 三重校验（语义级，非仅语法）；读侧兜底：接口失效 → fail fast 跳过并告警 |
| 生效语义 | 任务**下一次执行**读取新值（无 accepted≠applied 歧态：无运行中热切换，切换不打断进行中的抓取） |
| 影响范围 | 切源只影响**此后**新增/重刷报告期与日线的抓取来源，**历史数据保持原源不变**（增量策略不重抓历史）；如需用新源重建历史，须清空 `security_dividends` 并手动触发 `dividend_yield_rebuild` |
| 回滚 | 设置页改回原值即回滚；历史数据仍在（同表幂等，新源覆盖更新） |
| 审计 | `JobRunLog` 记录每次执行所用接口 id 与名称（结构化拼入 `message`，如 `interface=东财-分红配送(id=xxx); periods=2025Q4,2026Q1; rows=3377`）；配置变更经 `services/log.py` 的 `record()` 写 `AppLog`（level=info/warning），记录操作人、变更前后值 |
| 权限 | 配置端点需 `require_admin`；非 admin 在设置页看到只读或隐藏的控件 |
| 休眠功能守卫 | 未启用的接口行不进入设置页选项；接口页停用即从选项消失 |

### 6.8 每日公告扫描与特别分红补充 `dividend_notice_scan`（第 5 条系统任务）

> **为什么需要（决策 A6）**：东财按报告期接口系统性遗漏「无报告期归属的特别分红」
> （茅台 2022-12-27 派 219.1、2023-12-20 派 191.06 实测无记录，股息率被低估 38%~46%，
> 附录 A.6）。本任务用公告标题检测发现特别分红，再经新浪逐笔明细补充金额与状态。

- **触发**：每日 06:00（UTC+8，`0 6 * * *`，**含周末与节假日——按自然日扫描**）。
  > **必须扫自然日（实测）**：公告可发布于周六（茅台 2024 中期权益分派实施公告发布于
  > 2024-12-14 周六），接口按 `date` 精确匹配当日，**周一的返回不含周六公告**（附录 A.7）。
  > 漏扫周末即漏检；单日仅 1 次调用，成本可忽略。

- **第一步·公告获取（一级分类预过滤）**：数据源 =「公司公告」分类（id=4）配置的
  「沪深京 A 股公告」接口（SDK，`endpoint=stock_notice_report`，
  `params={"symbol": "财务报告", "date": "<当日YYYYMMDD>"}`）。实测分红实施公告
  **21/21 全部落在「财务报告」分类**（附录 A.7），预过滤把单日扫描量从 ~2000 条降到
  个位数~数十条。**不得改按「公告类型」列过滤**——该列是 ~150 种细粒度值
  （分配方案实施/分配预案/…）且值域随日期浮动。

- **第二步·标题正则二筛**（白名单维护在代码常量，改模式须补单测）：
  - 分红相关：`分红|派息|权益分派|利润分配|分配方案`（实测召回 20/21，唯一未中是
    「股东会决议公告」标题的边缘样本，附录 A.7）；
  - 候选特别分红：分红相关 **且** 含 `特别|中期`（决策 A11，实测依据附录 A.10：
    「东财缺失」的分红中，留存窗口内 3/3 标题含"特别"，如茅台「2022 年度回报股东特别分红
    实施公告」、开能健康「关于特别分红权益分派实施公告」；2 笔未命中均为 2005/2006 年，
    在 5 年留存窗口外，不影响）。纯「年度权益分派」为主源覆盖、不触发补充，
    避免分红季全市场误触发新浪逐只调用；含"中期"属冗余保险，命中后由西向去重跳过。
  - 取消/终止：含 `取消|终止` + 分红关键词 → 对应 SPECIAL 行置 `REJECTED`；
  - 「公告类型」列仅作参考字段落日志，不参与判定。

- **第三步·新浪逐只补充**：对命中证券调用**补充源**配置（§5.4
  `dividend_detail_source_interface_id`，当前「新浪-分红配股」）指向的接口
  （SDK，`endpoint=stock_history_dividend_detail`，按证券逐只，第四种调用形态见 §6.5）。
  实测**无频控**（40 只连续调用 0 失败，附录 A.8）；全国每月命中通常 <100 只，量级无忧。
  新浪行解析：`派息`（每 10 股）÷10 → `cash_per_share`；`进度=实施` 且除权日非空 → PAID。
  **新浪进度域覆盖不一致**（部分证券无预案行）→ 新浪只作「金额 + 实施事实」源，
  PROPOSED 的发现以公告标题为准。

- **写入与对账（SPECIAL 行）**：
  - 落格按 §2.1 公告日期锚点；`announcement_date` = 新浪行公告日期（实施行）或公告扫描命中日；
  - **西向去重**：写 SPECIAL 行前，若同 `master_id` 已有满足「`ex_dividend_date` 相等」**或**
    「`(report_year, report_quarter, cash_per_share)` 全等」的记录 → 跳过
    （该分红已被东财报告期行覆盖，如茅台 2024 中期分红在东财挂 2024Q3）；
  - **PROPOSED→PAID**：实施类命中后，按「同证券 + `cash_per_share` 相等」匹配存量
    PROPOSED SPECIAL 行（多行同额取 `announcement_date` 最近者）→ 置 PAID + 回填
    `ex_dividend_date`；无匹配则新建 PAID 行；
  - **存量复查**：每轮扫描对全部 `PROPOSED` 状态 SPECIAL 行所涉证券复查新浪一次
    （预案→实施/取消的状态迁移靠此收敛；量级 = 存量 PROPOSED 数，数十级）；
  - 取消/否决**不做超时自动否决**（会误杀延期实施），超 2 个报告期未实施置 `stale` 标记 + 站内信。

- **防击穿与事务**：公告接口每日 1 次调用；新浪逐只串行 + `_RATE_LIMITER` 限速；
  按证券独立 commit；失败记 `JobRunLog` 并续下一只，断点即数据本身（同 §6.1 语义）。

- **完成后**：对本次有变更的证券触发重算（仅变更集）。

## 8. 排名规则与过滤

### 8.1 管理页排序契约（强制）

```sql
ORDER BY dividend_yield DESC NULLS LAST, master_id ASC
```

> **为什么必须写全**：
> ① PostgreSQL 中 NULL 被视为大于任何非空值，`ORDER BY x DESC` **默认 NULLS FIRST**——
> 而 `dividend_yield` 确实可为 `null`（价格缺失，§3.5）。若漏写 `NULLS LAST`，
> **所有无股息率的证券会稳定占据第一页**，排名直接失效。
> ② 无 tiebreaker 时，同值行在分页间的顺序由 PG 自由裁量，`paged()` 又是裸 `limit/offset`
> （`services/base.py` L87-106），会导致**翻页重复行或漏行**。
> `master_id` 唯一且稳定，可保证分页与榜单可复现。

- **默认排序**：股息率降序（按上式）；各列可排序（股息率、每股分子、最新收盘价、连续分红年数、口径）。
- **过滤条件**（服务端参数化）：交易所、口径、`consecutive_years >= N`、是否含预案（`include_proposed`）、
  是否显示近两年无分红（`include_no_dividend`，**默认 false**）。

> 口径（TTM/LFY）列的排序应定义为**固定序**（TTM 优先于 LFY），而非字典序。
>
> `include_proposed=false` 时，过滤掉 `PROPOSED` 记录后**分子会随之改变**，
> 不能直接用快照的 `dividend_yield`。须定义"过滤态股息率"：由服务端按过滤后的记录集
> 现调 §2.5 纯函数计算，并在响应中标注该行使用的是过滤态口径（避免与快照值混淆）。

### 8.2 派生指标定义

- **连续分红年数 `consecutive_years`**：自**当前财年**（或当前财年尚未产生分红且仍在年内时，
  自最近一个已结束财年）起向前连续计数，某财年在 `security_dividends` 中无任何
  `PROPOSED`/`PAID` 记录即终止。上限受 5 年留存约束（最大 5）。

  > **与原定义的差异（重要）**：原定义"自最近一个有分红的财年向前连续计数"会导致
  > 只要历史分过一次红，连续年数就 **≥1、永远不会是 0**，从而与"近两年无分红即剔除"
  > 的规则脱节（2024 分红、2025/2026 停发的公司年数 = 1 却应被剔除）。
  > 改为"自当前财年起、断一年即止"后，近两年无分红的公司年数 = 0，两个规则天然自洽。

- **近两年无分红**：判定窗口 = **当前财年 Y 与 Y-1**（共 2 个财年，Y 允许不完整，按"至今"处理）。
  窗口内无任何 `PROPOSED`/`PAID` 记录 → 该证券**从展示页剔除**（管理页默认过滤，可手动关闭）。

  > 原表述"最近 2 个**完整**财年（含本年至今）"自相矛盾（"完整"与"含本年至今"互斥）。
  > 边界示例：2026 年 3 月运行时，窗口 = [2026, 2025]；2026 年尚无记录不单独构成剔除理由，
  > 需 2026 与 2025 均无记录才剔除。

- 二者均为分红事件的纯函数，随变更集重算落库（§5.3），**不在查询时现算**。

### 8.3 专门展示页（Top20）

- **榜单一：股息率 Top 20** —— 按 §8.1 排序契约取前 20，**剔除近两年无分红的公司**
  （避免僵尸记录污染榜单）；**并剔除 `suspicious = true` 的证券**（决策 A12：
  `yield ≤ 0` 或 `yield > 0.30`，一次性特别分红造成的畸高值不得占据榜首）。
  第 20/21 名同值时**不并列扩榜**，UI 需说明。

- **榜单二：连续分红公司榜** —— `consecutive_years >= 2` 的公司，按
  `consecutive_years DESC, dividend_yield DESC, master_id ASC` 排序；
  每行展示「连续 N 年分红」徽标与当前股息率。
  **条数上限确定取 20**（决策 A13，与 Top20 对称；不再保留 50 可配选项）——A 股符合条件者可能 2000+ 家，
  全量返回会带来 payload 与渲染性能问题，并在 §10.3 提供"查看全部 → 跳转管理页带
  `min_consecutive` 过滤"的出口。

## 9. API 契约（新增 `app/modules/dividend_yield/` 路由）

| 端点 | 方法 | 鉴权 | 说明 |
| --- | --- | --- | --- |
| `/api/dividend-yield/rankings` | GET | `get_current_user` | 分页排名，参数 `sort/order/exchange/mode/min_consecutive/include_proposed/include_no_dividend`；返回行含股息率、分子、收盘价、口径、连续年数、stale |
| `/api/dividend-yield/{master_id}/curve` | GET | `get_current_user` | 过去一年逐交易日股息率序列 `[{trade_date, close, yield, numerator}]` |
| `/api/dividend-yield/{master_id}/implied-price` | GET | `get_current_user` | 反推价格：入参 `target_ratio`（**小数**，如 0.05），返回 `implied_price = numerator / target_ratio` 及当前分子、当前价、当前股息率对照 |
| `/api/dividend-yield/top20` | GET | `get_current_user` | 展示页聚合：Top20 榜 + 连续分红榜（剔除逻辑见 §8.2/§8.3） |
| `/api/dividend-yield/settings` | GET | `get_current_user` | 读取全局配置（阈值 + 数据源）+ 各分类 enabled 接口选项 |
| `/api/dividend-yield/settings` | PUT | **`require_admin`** | 更新全局配置（§5.4 三重校验，fail closed 400） |

> **命名**：路径与 DTO 一律使用 `master_id`，**不得**使用 `security_id`（§4 命名约束）。
> **单位**：所有比率字段为**小数**（0.05 = 5%）；用户输入项 `target_ratio` 亦为小数。

**曲线口径契约（一致性强制）**：

- 逐点复用 §2.5 的 `dividend_yield()` 纯函数，输入为「**截至该交易日可见的分红记录集** +
  该日收盘价」。"可见"的判定锚点为 `ex_dividend_date`；该字段为 NULL 时回退
  （`COALESCE(ex_dividend_date, 锚点日)`）：报告期行用 `(report_year, report_quarter)` 的
  **期末日**作锚点（如 Q2 → 06-30、Q4 → 12-31），SPECIAL 行用 `announcement_date`
  （公告日，§3.6）。
- **契约：曲线最后一个点的股息率必须等于该证券快照值。** §12 须有对应断言。
- 这是对"历史时点预案状态"的近似（无法回放当时是否已否决），接受该近似；
  `ref_div_ids` 仅对当前快照负责，曲线不承诺点时精确状态。
- 响应每点须含 `numerator_per_share`，供前端叠加"分子不变段"提示（§10.2）。

**复用既有 API 设施**（不新写分页/排序基建）：

- 分页：复用 `services/base.py` 的 `paged()`（L88-106）+ 路由层 `common.py` 的统一响应包装
  `{"items,total,page,pageSize}`（L38-47）。注意 `paged()` 每页执行 `count(subquery)`，
  ~3500 行规模下可接受。
- 排序：`sort` 参数**白名单校验**，前后端模式参照 cashflow 模块
  （`query-params.ts` 的 `parseSortParam` 白名单 + `TransactionsPage` 的
  `sortBy/sortOrder` URL-query 透传）。

### 11.2 迁移链（**单一** `0003`，不可拆成两份）

> **原风险**：原《股息率计算方案》§5.4 定 `0003_dividend_yield.py`、本方案定
> `0003_dividend_yield_ranking.py`，**两者 `down_revision` 同为 `0002_dividend_list_category`**
> → Alembic 出现多个 head，`alembic upgrade head` 直接失败。现已合并为一份文档，
> 迁移亦合并为**一条**。

新增 `0003_dividend_yield.py`，`down_revision = "0002_dividend_list_category"`。内容：

1. **建 5 张表**：`security_dividends`（唯一键含 `period_type`，§5.1）、`market_security_daily_prices`、
   `security_dividend_yields`（含 `suspicious` 列，§5.3）、`dividend_yield_settings`
   （主源/补充源双字段，§5.4）、`market_trade_calendar`（§5.5），含索引（见 §5.3）；
2. **新建枚举类型**：`DividendYieldMode` / `DividendStatus` / `ReportPeriodType`
   用 `postgresql.ENUM(..., create_type=True)`（新建类型，须显式 True）；
3. **`JobTaskType` 扩展 5 值**（含 `DIVIDEND_NOTICE_SCAN`）：必须在 `ctx.autocommit_block()` 中执行
   `ALTER TYPE "JobTaskType" ADD VALUE IF NOT EXISTS '...'`；
4. **分类与接口行 seed（幂等）**：新分类「公司公告」（id=4）+ 四条接口行——
   「东财-分红配送」（分类 3）、「腾讯财经-A股...行情」（分类 2）、「沪深京 A 股公告」（分类 4）、
   「新浪-分红配股」（分类 3），`WHERE NOT EXISTS` 保护；
5. **系统任务种子**：5 条 `INSERT ... WHERE NOT EXISTS (SELECT 1 FROM job_configs WHERE name=...)`
   含中文名/cron/`kind='SYSTEM'`/`enabled`；**种子 INSERT 必须在枚举 ADD VALUE 提交之后执行**
   （否则 `CAST(:task_type AS "JobTaskType")` 报错）；
6. **配置表默认行**：阈值 0.05/0.03，数据源默认取分类内 `priority` 最小 enabled 接口。

> **为什么必须 seed 接口行**：已核实 `backend/alembic/versions/` 中
> `quote_provider_interfaces` **只有建表/改表 DDL，无任何 INSERT**（当前开发库的接口行是人工录入）。
> 若不 seed，全新部署或 CI 测试库执行 `alembic upgrade head` 后，分类 3 下无任何 enabled 接口
> → 默认解析为 NULL → 任务按 §6.5 fail fast → **整条链路静默不产出任何数据**。
> 若出于"接口配置属运营数据"考虑不 seed，则必须在上线手册写明该人工步骤，
> 并说明测试库如何保证有一份。

**downgrade 边界**：表与列可 drop；**新增枚举值不回收**
（`AGENTS.md` §3：PG 不支持 `ALTER TYPE ... DROP VALUE`）。
原《计算方案》§6 要求的"upgrade head + downgrade 往返幂等"对枚举而言**物理不可实现**，
该断言须改为"表结构可往返、枚举值不回收"。

### A.11 `stock_zh_a_hist` 回补限速实测（§6.2 / 决策 A15 依据，2026-09-06）

接口：akshare `stock_zh_a_hist`（后端 `push2his.eastmoney.com`）。有界探针 26 只、5 年日线。

- **单只耗时极低**：成功调用 0.16–0.31s（avg 0.21s），单次返 ~1376 行（5 年日线）。
- **突发即限流**：前 18 只（间隔 0.3–0.6s）成功，之后**连续 `ProxyError`/`MaxRetryError`
  （连 push2his 被拒）**——约**累计 18 次快速请求触发东财限流**，0.6s 节奏也未能避免
  （是累计量触发，非瞬时速率）。
- **冷却 >60s**：限流后停 60s 再试仍 `ProxyError` → 冷却窗口以分钟计。
- **对比**：同为东财的 `stock_fhps_em`（股息主源）实测"服务端不限流"（附录 A.5），
  **push2his 明显更严**——回补不可复用主源 `rate_limit`，须独立更保守节奏。

**推导策略（决策 A15）**：burst≈10 只 + 冷却 60–120s + 指数退避（60/120/300s）；
3000 只外推 ≈ 300 批 × (10×0.25s + 90s) ≈ **5–8 小时**，多小时、**可断点续跑**后台任务；
须持久化已回补进度（按证券），每批记进度日志，经 §6.7 系统任务执行日志只读呈现，
**不新增设置项**。
